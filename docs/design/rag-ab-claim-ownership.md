# RAG A/B 작업 소유권과 트랜잭션 경계

## 관측된 문제

격리된 PostgreSQL과 백엔드 JVM 두 대를 사용한 수정 전 시험에서 검색 요청 1건의 모델 호출이 2회 발생했다. 앱 A가 모델 응답을 기다리는 동안 앱 B가 기동했고, B의 시작 복구가 `PROCESSING` 작업의 `claimed_at`을 지운 뒤 같은 작업을 다시 선점했다. 이 시험은 제어 가능한 모델 서버를 사용했으며 공개 서비스 또는 실제 Ollama의 결과가 아니다.

## 목표와 경계

1. 모델 응답 대기 중 DB 트랜잭션과 커넥션을 유지하지 않는다. 답변과 인용은 한 트랜잭션에서 확정한다.
2. 선점 시 인스턴스 소유자, 매번 바뀌는 토큰, 만료 시각을 기록한다. 살아 있는 작업은 lease를 연장한다.
3. 앱 기동 시 전체 선점 해제를 제거한다. 미선점 또는 만료된 작업만 행 잠금으로 재획득한다.
4. 완료 쓰기는 현재 토큰과 `PROCESSING` 상태가 모두 맞을 때만 허용한다. 늦게 도착한 이전 소유자의 결과는 폐기한다.
5. 기존 90초 최종 타임아웃은 유지한다. 만료된 작업도 이 제한 안에서만 재개하며, 성공과 타임아웃 중 먼저 확정된 한 상태만 남긴다.

## 검증

- A 모델 호출 중 B 기동: 유효한 claim 유지, 같은 작업의 모델 호출 1회.
- A 중단: lease 만료 후 B 재선점, 최종 답변과 인용 한 벌.
- A의 늦은 결과: 옛 토큰의 완료 UPDATE 0행.
- 스위퍼 경합: 최종 상태 하나와 알림 중복 없음.

모델 요청을 보낸 직후 프로세스가 죽으면 외부 호출 자체는 재시도 과정에서 다시 일어날 수 있다. 보장 대상은 모델 호출 정확히 1회가 아니라 DB에 확정되는 최종 결과의 소유권과 일관성이다.
