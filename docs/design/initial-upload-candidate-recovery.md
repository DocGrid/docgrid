# 최초 업로드 GCS 후보 복구와 안전한 정리

최초 문서 업로드에 `Idempotency-Key`가 있으면 GCS 저장 **전에** 요청 원장에 객체 위치, 입력 SHA-256, 크기를 별도 DB 트랜잭션으로 기록한다. 앱이 GCS 저장 직후 종료돼도 5분 소유권 리스가 만료된 뒤 같은 사용자·키·입력으로 재시도하면 그 후보를 다시 검사한다. 바이트 해시와 크기가 같을 때만 문서·버전·Outbox·Job 생성에 재사용한다. 후보가 아직 없으면 **같은 객체 키**로 저장해 늦게 끝나는 이전 업로더의 객체가 추적 밖에 남지 않게 한다. GCS 쓰기는 `doesNotExist` 조건을 사용하며, 경합으로 쓰기가 실패하면 후보를 다시 읽어 검증한다.

```text
요청 원장 IN_PROGRESS + 후보 없음
  → 후보 키·SHA-256·크기 DB 커밋 → GCS 조건부 생성
  → DB 트랜잭션에서 FileObject·Document·Version·Outbox·Job·완료 응답 커밋

저장 직후 앱 중단
  → 후보 위치는 DB에 남음 → 리스 만료 → 같은 키 재시도
  → 실제 객체의 SHA-256·크기 검사 → 일치하면 재사용, 불일치면 503으로 보류
```

기존 `FileObject`를 재사용하거나 경합으로 다른 `FileObject`가 채택되면 미사용 후보 위치는 완료 원장에 남긴다. GCS 외부 객체와 DB 트랜잭션은 원자적이지 않으므로 별도 정리가 필요하다.

## 정리 경계

기본 스케줄러는 한 시간마다 등록 후 24시간 지난 후보를 **최대 100건 조회하여 집계만** 한다. `document.upload.candidate-delete-enabled=true`를 명시해야 삭제가 시작된다. `document.upload.candidate-reconcile-enabled=false`로 스케줄러를 끌 수 있고, `document.upload.candidate-grace-hours`와 `document.upload.candidate-reconcile-interval-ms`로 유예 시간과 주기를 조정할 수 있다. 실제 삭제 활성화 전에는 보존 기간·권한·시험 환경의 결과를 확인해야 한다.

```text
오래된 후보 발견
  → DB 정리 예약 커밋: 이전 업로더 토큰 무효화, CLEANING 상태
  → FileObject 참조 조회
     ├─ 참조됨: GCS 삭제 없이 후보 표시만 해제
     └─ 미참조: GCS generation 고정 읽기 + SHA-256·크기 검사
          ├─ 일치: 해당 generation만 조건부 삭제, 후보 표시 해제
          ├─ 객체 부재: 지연 업로드에 대비해 후보 위치 유지
          └─ 불일치·저장소 오류: 후보 위치 유지, 다음 회차 재검사
  → DB 정리 예약 해제; 미완료 요청은 재시도 가능한 상태로 복귀
```

정리 예약은 외부 삭제 전에 커밋되어, 이전 업로더가 나중에 DB 트랜잭션을 완료하려 하면 소유권 토큰 검사에서 롤백된다. 삭제는 GCS 객체 세대가 검사 당시와 같을 때만 수행한다. 정리 프로세스가 중단되면 예약 리스 만료 후 다시 검사할 수 있다. 객체가 없다는 관찰만으로 후보 기록을 지우지 않으므로, 매우 늦게 끝난 GCS 쓰기도 같은 위치에서 추적된다.

이 구현의 자동 삭제는 **GCS 후보만** 지원한다. 다른 저장소는 후보 재시도 검사 대상이지만 자동 삭제는 보류한다. 로컬 PostgreSQL과 모의 GCS 어댑터 시험은 실제 Cloud Run·GCS·OpenSQL 장애의 결과가 아니다. 실환경 장애 주입과 복원 시간·중복 결과 측정은 별도 시험이 필요하다.
