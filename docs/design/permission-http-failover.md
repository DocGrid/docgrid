# 실제 HTTP 권한 회수·승격 경계 검증 설계

## 범위와 전제

이슈 #542. 공개 설정·계정·데이터를 변경하지 않는다. 기존 라이선스 호스트의 별도 컨테이너·데이터·포트·DCS에서 strict 지정형 동기를 사용하고, 기존 읽기 전용 역할 어댑터 경유를 명시한다.

로컬 루프백 HTTP 서버의 실제 SecurityConfig·로그인·JWT·Valkey·Controller·권한 원장과 검색 접수·결과 저장을 사용한다. 파일은 메모리의 합성 바이트, 임베딩·검색 후보·답변은 제어 가능한 시험 대역이다. 공개 브라우저·실제 모델 품질·GCS·과거 대화 재조회는 범위 밖이다.

## 순서와 완료 기준

1. 소유자와 대상 사용자, 회수 대상·대조 문서, 원본 바이트·Chunk·Embedding·READ 원장을 격리 DB에 생성한다. 비밀번호·JWT는 메모리에서만 사용한다.
2. 실제 /auth/login으로 인증한다. 인증 없는 상세 요청은 401, 두 문서의 상세·본문·파일은 200, 검색은 두 합성 문구·근거를 포함해야 한다.
3. 실제 DELETE 회수 요청을 키 K로 보내 204를 확인한다. 오래된 USER 캐시를 시험 목적으로 다시 유효하게 만들고 새 요청의 차단을 확인한다.
4. 외부 제어기가 시험 Primary만 종료하고 후보 지정 없이 자동 승격을 관측한다. 이전 Primary는 중지한 채 새 Primary 경로를 확인하며 재가입은 별도 자원 복구로 구분한다. 회수 확정 시각 뒤 새 HTTP 요청을 사용한다.
5. 대상 상세·본문·파일은 403, 새 검색은 200이면서 대상 문구·문서 ID·근거가 없고 대조 문구·근거는 있어야 한다. 대조 문서 상세·본문·파일은 200이다. 반복 3회 측정한다.
6. 현재 Primary에서 K 원장 1개·권한 행 0개를 대조한다. 503 전체를 통과로 처리하지 않으며 장애 직후 과도 구간 오류는 별도 기록한다.

## 증거와 비밀 보호

각 HTTP 응답에서 시각·단계·논리 문서 별칭·상태·지연·금지 문구 검출 여부·응답 SHA-256만 즉시 보존한다. 이메일·비밀번호·토큰·Authorization·실제 계정·인프라 주소·원시 로그인 응답을 출력하거나 파일에 쓰지 않는다. 실행 디렉터리는 재사용하지 않는다. 실패·재시험·공개 설정 hash·최종 정리 기록을 분리한다.
