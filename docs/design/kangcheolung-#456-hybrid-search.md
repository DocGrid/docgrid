# #456 하이브리드 검색: 벡터 + 희귀 단어 가중 키워드 점수 결합

- 관련 이슈: closes #456
- 작성일: 2026-10-10
- 상태: 구현·테스트·측정 완료 (커밋 전). 기능 플래그 `search.hybrid.enabled` 기본값 **켜짐** — `SEARCH_HYBRID_ENABLED=false`로 즉시 기존 벡터 단독 검색으로 되돌릴 수 있다.

## 1. 배경

멘토링에서 "벡터 검색에 키워드 검색을 함께 쓰는 하이브리드 방식"을 고려해 보라는 개선안이 나왔다. 지금 검색은 벡터(코사인 유사도) 하나로만 순위를 매기고 거른다.

```
벡터 거리순 후보(topK×4) → 유사도 0.30 미만 제거 → 문서당 2개 상한 → 상위 topK
```

### 1.1 확인한 문제

| # | 문제 | 근거 |
|---|---|---|
| ① | `OM`, `SSE`, `Pub/Sub`처럼 짧은 용어·약어를 묻는 질문에서 정답을 못 찾는다 | `OM은 뭐야?`는 정답이 7위라 AI에게 전달되지 않았고 AI가 "관련 문서를 찾지 못했습니다"라고 답했다 |
| ② | 문서에 없는 질문에도 관련 없는 청크가 5건씩 붙는다 | 점수만으로는 정답 있는 질문(1위 0.41~0.88)과 없는 질문(0.38~0.52)이 겹쳐 기준값 하나로 가르지 못함. 다만 AI가 스스로 거절해서 사용자가 보는 답변은 대체로 맞다 |
| ③ | ②를 막으려고 기준값을 올리면 식별자 질문이 먼저 잘려 나간다 | 기준값 0.30→0.50→0.55에서 식별자 질문 1위 비율 0.714→0.571→0.357 |

문서의 단어를 쓰지 않고 바꿔 쓴 질문은 벡터가 이미 잘 처리하므로 이 성능은 유지해야 한다.

## 2. 첫 설계가 일반화에 실패한 경험

처음에는 "벡터 갈래 + `pg_trgm` 키워드 갈래를 RRF로 합치는" 구조로 구현해 측정했다. 키워드 점수는 질문 **문장 전체**와 청크의 글자 조각 겹침(`word_similarity`)이었다.

| 질문 세트 | 벡터 단독 1위 정답 | 첫 설계(RRF) 1위 정답 |
|---|---:|---:|
| 설계를 정하는 데 쓴 세트 (34개) | 26 | **28** |
| 처음 보는 세트 (38개) | 28 | **24** (좋아진 2 / 나빠진 6) |

**설정을 고른 질문에서는 좋아 보였지만 처음 보는 질문에서는 벡터 단독보다 나빴다.** 원인은 두 가지였다.

1. RRF는 "키워드 순위에 들었는가"에 큰 가산점을 주고 순위 차이는 작게 반영한다. 정답이 벡터 1위인데 키워드 점수가 기준에 조금 못 미치면(예: 0.25 < 0.30) 순위 가산이 없고, 기준을 넘은 오답이 가산점을 받아 앞선다.
2. 문장 전체의 글자 조각 겹침은 `누구야`, `어떤` 같은 **질문 말투**까지 점수에 반영해서 내용과 무관한 청크가 키워드 점수를 받는다.

기준값(0.50/0.30)의 문제가 아니라 신호를 합치는 방식과 키워드 점수의 질이 문제였다. 이 경험으로 검증 방식을 바꿨다(§4).

## 3. 최종 설계

```
SearchFacade
  ├─ 임베딩(문맥 포함) → permittedIds (기존)
  └─ search.hybrid.enabled=true 이면 HybridSearchQueryService.search(벡터, 원문 질문, 모델, permittedIds, topK)
        ├─ 질문 단어 추출 : 소문자, 공백·문장부호로 분리, 끝 조사 제거, 질문 말투(불용어)·한 글자 제거
        ├─ 단어 가중치(IDF) : 검색 범위(허용 문서) 안에서 그 단어가 든 청크 수 df → 가중치 = ln((N+1)/(df+0.5)), 범위에 없는 단어는 제외
        ├─ 커버리지       : 청크가 가진 단어의 가중치 합 / 전체 가중치 합 (0~1). 영문·숫자 단어는 단어 경계로, 그 밖은 부분 문자열로 일치
        ├─ 후보           : 벡터 상위 + 커버리지 ≥ τc 상위 + 벡터 후보의 커버리지
        ├─ 관련도 판정    : (벡터 유사도 ≥ τv) OR (커버리지 ≥ τc) 가 아니면 제외
        ├─ 순위 점수      : 벡터 유사도 + α × 커버리지   (순위만 쓰는 RRF를 쓰지 않는다)
        └─ 문서당 상한을 결합한 순서에 적용 → topK
  SEARCH_HYBRID_ENABLED=false로 끄면 기존 VectorSearchQueryService 경로가 그대로 동작한다(롤백 스위치).
```

- **벡터가 순위를 주도하고 단어 일치는 작은 보너스**다(α = 0.1). 단어가 겹친다는 이유만으로 벡터 1위 정답이 밀리지 않고, `OM`처럼 벡터가 의미로 못 잡는 용어는 그 단어를 가진 청크가 커버리지로 결과에 들어온다.
- 흔한 단어(`STOMP`가 22개 청크)는 가치가 낮고 드문 단어(`OM`이 1개 청크)는 높아서, "주제만 같은 청크"보다 "질문의 드문 단어까지 가진 청크"가 위로 간다. 검색엔진의 TF-IDF/BM25 아이디어를 직접 구현했고 새 의존성은 없다.
- 키워드 방식으로 `tsvector('simple')`는 "고구려는", "@MessageMapping으로"처럼 조사가 붙은 토큰을 통째로 한 단어로 봐서 쓰지 않았다. 단어 일치는 PostgreSQL 정규식(`~*`)으로 하고 `pg_trgm` GIN 인덱스(V45)가 후보 조회를 돕는다.
- 키워드로만 잡힌 청크도 쿼리가 벡터 거리를 함께 계산해 응답·저장의 `similarityScore`를 모든 후보가 가진다. 응답 스키마와 `search_results` 변경은 없다.

### 3.1 설정 (`search.hybrid.*`)

| 키 | 기본값 | 의미 |
|---|---|---|
| `enabled` (`SEARCH_HYBRID_ENABLED`) | `true` | 하이브리드 사용 여부. false면 벡터 단독 |
| `vector-min-similarity` (τv) | 0.45 | 이 이상이면 단어가 안 겹쳐도 인정 (하이브리드에서만 사용) |
| `min-coverage` (τc) | 0.50 | 질문 단어 가중치의 이 비율 이상을 가지면 벡터 유사도가 낮아도 인정 |
| `coverage-weight` (α) | 0.10 | 순위 점수 = 벡터 유사도 + α × 커버리지 |
| `lexical-candidate-pool-multiplier` | 4 | 단어 후보 풀 = topK × 배수 |

기존 `search.vector.min-similarity`(0.30)는 변경하지 않으며 하이브리드를 끈 경우에만 쓰인다. `max-chunks-per-document`와 `candidate-pool-multiplier`는 하이브리드에서도 그대로 쓰인다.

### 3.2 API·스키마 영향

- 엔드포인트와 응답 스키마 변경 없음. 결과가 0건일 수 있는 것도 기존과 같다(`200` + 빈 결과, RAG는 고정 안내 문구).
- DB: Flyway V45 — `pg_trgm` 확장과 `document_chunks.chunk_text` GIN 인덱스만 추가한다. 테이블·컬럼 변경과 재임베딩은 없다.
- 에러 케이스는 기존과 같다(임베딩 서버 지연 504 `SEARCH-004` 등). 단어 쿼리 실패는 기존 검색 실패 처리(`search_queries` FAILED 확정)를 따른다.

## 4. 검증

### 4.1 방법

- 코퍼스: 사용자가 읽을 수 있는 5개 문서(WebSocket 공부자료 MD, SOLID MD, 교육팀 PDF, 디렉토리 명령어 TXT, 회칙 MD), 청크 83개. 공유 DB 화면과 7개 질문에서 순위·점수가 동일함을 확인한 로컬 DB에 같은 파서·청커로 인덱싱했다.
- 질문은 서로 겹치지 않는 세 세트다. 유형은 약어·용어·수치·이름·명령어 옵션(식별자), 바꿔 쓴 자연어(의미형), 한영 혼합, 문서에 없는 질문이다.
  정답은 청크 번호가 아니라 **근거 문구**가 모두 들어 있는 청크로 판정한다(교육팀 PDF와 WebSocket MD가 같은 내용이라 어느 쪽이든 정답).
- **세트 1(34+8)**: 설계와 설정(τc, α)을 정하는 데 사용. **세트 2(38+6)**: 첫 설계의 일반화 검증. **세트 3(39+6)**: 최종 설계와 판정 기준을 **결과를 보기 전에 파일로 고정**
  (`design-frozen-before-set3.txt`)한 뒤 처음 사용. 판정 기준은 벡터 단독 대비 ① 1위 정답 수 이상 ② 3위 안 정답 수 이상 ③ (좋아진 질문 − 나빠진 질문) ≥ 2 ④ 의미형에서 1위·3위 안 모두 이상이다.
- 실제 서버(로컬 DB, 임베딩 BGE-M3)에 `POST /search`(topK 10, 컬렉션 범위 지정)를 보내 정답 순위로 Hit@k·MRR@10을 계산했다. 측정 중 RAG 생성이 같은 기기의 CPU를 점유해 임베딩이 5초 제한을 넘기는 문제가 있어
  순위 측정 서버는 Ollama 주소를 닿지 않는 곳으로 돌려 생성을 즉시 실패시켰다. 실제 답변 비교는 Ollama를 연결한 별도 실행으로 했다.
- 증빙: `docs/test-results/evidence/issue-456/` (질문 세트 3개, 측정 스크립트, 실측 JSON, 실제 답변 12개). 설계 검토 중 쓴 파이썬 재현은 실서버 결과와 세트 2·3에서 일치했다.

### 4.2 결과 (실제 서버, 벡터 단독 → 새 하이브리드)

| 세트 | 정답이 1위 | 정답이 3위 안 | MRR@10 | 좋아진 / 나빠진 질문 |
|---|---:|---:|---:|---|
| 1 (34개, 설계에 사용) | 26 → 28 | 32 → 33 | 0.847 → 0.887 | 2 / 0 |
| 2 (38개) | 28 → 32 | 33 → 34 | 0.806 → 0.864 | 4 / 1 |
| **3 (39개, 사전 고정 기준)** | **28 → 32** | **32 → 36** | **0.784 → 0.868** | **8 / 0** |
| 합계 (111개) | 82 → 92 (0.739 → 0.829) | 97 → 103 | 0.811 → 0.872 | 14 / 1 |

세트 3은 사전 고정한 4개 기준을 모두 충족했다(1위 32 ≥ 28, 3위 안 36 ≥ 32, 좋아진−나빠진 = 8, 의미형 1위 8 ≥ 7·3위 안 9 ≥ 8).

좋아진 사례는 `OM은 뭐야?`(7위→1위), `Pub/Sub 기능이 없다는 게 무슨 뜻이야?`(7위→1위), `WebSocket은 구현 복잡도가 어때?`(4위→1위) 등이다. 나빠진 1개는 `ISP는 뭐의 약자야?`(6위→결과 밖)이다.

### 4.3 실제 AI 답변 비교 (12개 질문, Ollama `qwen2.5:7b`, 질문당 1회)

| 비교 | 질문 수 | 내용 |
|---|---:|---|
| 하이브리드가 명확히 나음 | 3 | `OM은 뭐야?`와 `WebSocket은 구현 복잡도가 어때?`는 벡터 단독에서 **"관련 문서를 찾지 못했습니다"** 였는데 정답을 답함. `ls 파일1은 뭘 보여줘?`는 벡터 단독 답변에 문서에 없는 내용(크기·수정 날짜·권한)이 섞였는데 하이브리드는 문서 내용만 답함 |
| 차이 없음 | 9 | 검색 순위가 개선돼도(`회칙은 어떻게 바뀔 수 있어?` 정답 4위→2위 등) AI가 같은 답을 했거나, 둘 다 같은 결과 |
| 하이브리드가 나쁨 | 0 | |

첫 설계에서 나빠졌던 `STOMP에서 /app은 어느 방향이야?`와 `rm -rf의 -f 옵션은 뭐야?`는 새 설계에서 벡터 단독과 같은 정답 순위·답변이다.
AI 답변은 매번 조금씩 달라서(번역문이 덧붙거나 말투가 바뀜) 이 비교는 사례 확인용이다.

## 5. 한계 (결과를 읽을 때 반드시 고려)

- **질문 수가 적고 5개 문서(청크 83개) 규모다.** 질문 하나가 Hit@1을 약 3%p 움직인다. 질문은 직접 작성했고 실제 사용자 질문 분포와 다를 수 있다.
- **세트 1은 설계에, 세트 2는 설계 선택(첫 설계 폐기와 재설계 방향)에 영향을 줬다.** 세트 3만 최종 설계 고정 이후의 검증이고, 이 결과도 한 번의 측정이다. 코퍼스가 커지면 기준값과 가중치를 다시 점검해야 한다.
- **문서에 없는 질문 걸러내기는 이 설계의 강점이 아니다.** 결과가 완전히 사라지는 비율이 세 세트에서 3/8, 1/6, 0/6이고 평균 반환 건수는 5건에서 1.3~3.5건으로 줄었을 뿐이다.
  질문 단어가 일부 겹치면 관련 없는 청크도 통과하기 때문이다. 사용자 눈에 보이는 답변은 AI가 이미 거절하므로 대체로 같다.
- **질문을 단어로 나누는 규칙은 단순하다**(조사 목록, 불용어 목록). 형태소 분석이 필요한 질문은 단어가 틀리게 잡힐 수 있고, 그 경우 벡터 순서에 가까운 결과가 나온다. 규칙은 한국어 문서 위주로 정했다.
- **한영 혼합 질문(세트 3에서 4개)과 같은 주제 청크가 여럿인 질문은 개선 폭이 작다.** 첫 설계에서 문제였던 `STOMP /app`류는 해결됐지만 근본적으로는 "주제가 같다"와 "답이 있다"를 단어 일치로 구분할 수 없다.
- **검색 비용이 늘어난다.** 요청마다 단어 문서 빈도 조회, 단어 커버리지 조회가 추가된다(DB 왕복 +2). 5개 문서에서는 응답시간 중앙값이 벡터 단독과 같았다(약 280~305ms, 클라이언트 측, 질문 임베딩 포함).
  청크가 수만 개 이상이면 정규식 조회 비용이 커질 수 있고 큰 코퍼스에서는 측정하지 않았다. 필요하면 문서 빈도를 캐시하거나 후보를 제한해야 한다.
- AI 답변 비교는 12개, 질문당 1회라 확정적이지 않다.

## 6. 배포·운영 주의

- **`pg_trgm` 확장은 DB 관리자가 미리 설치하는 것이 안전하다.** `vector` 확장도 마이그레이션이 아니라 사전 설치 방식이다. V45의 `CREATE EXTENSION IF NOT EXISTS`는 이미 설치돼 있으면 변경 없이 통과하지만,
  마이그레이션 계정에 DB `CREATE` 권한이 없고 확장이 없으면 앱 기동이 막힌다. `pg_trgm`은 trusted 확장이라 `CREATE` 권한만 있으면 설치할 수 있다(공유 OpenSQL에서 `pg_trgm` 1.6 사용 가능·trusted·미설치 확인).
- GIN 인덱스 생성은 `document_chunks`의 쓰기를 잠시 막는다(`CONCURRENTLY`는 Flyway 트랜잭션 안에서 쓸 수 없다). 청크 수가 많은 환경에서는 점검 시간에 적용한다.
- 이 브랜치의 백엔드를 공유 DB(`opensql-ha`)로 실행하면 V45가 공유 DB에 적용된다. 합의 전에는 로컬 DB로만 실행한다.
- **기본값이 켜짐이므로 배포하면 검색 동작이 바뀐다.** 결과 순서가 달라지고 문서에 없는 질문은 결과가 줄거나 없어질 수 있다. 롤백은 `SEARCH_HYBRID_ENABLED=false`(재시작 필요)이며 확장과 인덱스는 남아도 해롭지 않다.
- 기본값 변경(`search.vector.min-similarity` 포함)은 이번 범위가 아니다(#190). 하이브리드의 `vector-min-similarity`(0.45)는 하이브리드 경로에서만 쓰인다.
- 단어 일치는 정규식이라 질문에 정규식 특수 문자가 있어도 이스케이프해서 전달한다(`QueryTermExtractorTest`).
