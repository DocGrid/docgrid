# 특정 WAL의 외부 보존 완료 경계

관련 이슈: #563. #562의 성공 응답 65건 중 33건 복원 결과에서 확인한 외부 WAL 최신성 공백을 다룬다. 공개 PostgreSQL·Patroni·Barman 설정이나 개인 환경 파일을 변경하지 않는다.

## 기존 동작과 보완 범위

기존 외부 복사 명령은 Barman `wals` 디렉터리의 완성 파일을 복사하고 명령 완료 시각을 기록한다. 이는 복사 작업의 성공이며, 특정 업무의 최신 변경을 포함한다는 뜻은 아니다. 앞선 격리 시험은 WAL 전환 뒤 2초 대기와 `archive-wal` 한 번으로 완료를 추정했다.

설치된 Barman 3.19.1의 `StreamingWalArchiver.get_next_batch`는 미완성 파일을 보류하고, `.partial`이 없는 경우 마지막 완성 파일 하나도 재시작 위치를 위해 남긴다. 수신·파일 전환·archive 호출의 시간 차이를 완료 조건으로 취급하면 안 된다. 실제 재현 결과와 준비 중단은 `docs/test-results/`에 별도로 기록한다.

```text
그림 1 — 기존 판정과 필요한 완료 조건 [설계]

호출자: 성공 응답 구간의 마지막 쓰기가 완료됨
  → PostgreSQL WAL 전환 → 필요한 완성 WAL 이름 확보
  → 수신 프로세스가 파일을 닫고 다음 위치로 진행
  → Barman 보관 디렉터리에 해당 파일 도착
  → 외부 저장소 복사 → 해당 파일의 원격 바이트 무결성 확인
  → 이 구간의 보존 완료로 기록

고정 2초 대기나 archive 명령 종료 코드만으로는
위의 '필요한 파일 도착'과 '원격 바이트 일치'를 대신할 수 없다.
```

## 기존 스크립트에 추가할 계약

`barman_offsite_sync.py`에 `wait_for_archived_wal`을 추가한다. 호출자가 이미 정한 24자리 대문자 WAL 이름과 Barman 보관 디렉터리를 입력한다. 최대 300초 이내의 단조 시계 제한을 두고 `archive-wal`을 반복하며 그 파일이 실제 보관되기까지 기다린다. 다른 파일·history·활성 `.partial`·빈 파일·심볼릭 링크를 완료로 세지 않는다.

```text
그림 2 — wait_for_archived_wal과 sync 내부 [설계]

sync(required_wal)
  → WAL 이름·제한 시간 검증
  → archive-wal 반복
       ├─ 정확한 완성 파일 미도착: 남은 시간 내 다시 확인
       ├─ 명령 오류·시간 초과: 실패 반환
       └─ 정확한 파일 도착: 크기·CRC32C 확보
  → 기존 sync_wals 실행
  → 외부의 같은 경로 크기·CRC32C 대조
       ├─ 누락·불일치: 실패, last_success_utc 유지
       └─ 일치: required_wal_verified=true와 완료 시각 저장
```

CLI는 명시적인 `sync --required-wal <WAL> --wait-timeout 120` 옵션으로 사용한다. 인자 없는 기존 복사 타이머의 동작·설정 파일·환경변수는 유지한다. 그 타이머의 health는 계속 복사 최근성 점검이며 업무 데이터 최신성이나 RPO 보장이 아니다. 이 함수는 원본 WAL 전환이나 PostgreSQL 설정 변경을 직접 수행하지 않는다.

호출자는 전환 뒤 수신의 다음 파일 진행도 확보해야 한다. 격리 시험에서는 전환 뒤 합성 `pg_create_restore_point` WAL을 생성하는 방식을 별도로 비교한다. 이를 위해 공개 `archive_timeout`·`synchronous_commit`·Patroni 정책을 바꾸거나 Barman의 마지막 파일 보호 로직을 제거하지 않는다. 실제 효과는 재현 로그로 판정한다.

## 검증·재시험

- 단위 계약: 지연 도착, `.partial`·다른 파일 제외, 시간 초과·잘못된 시간 설정, archive 오류, 원격 누락·불일치, 이전 성공 시각 유지, 기존 복사 동작 회귀.
- 실제 재현: 전용 논리 DB·같은 Barman 3.19.1 수집기로 기존 방식과 이름 기반 완료 대기를 대조한다. 수집기 준비 실패를 WAL 경합 재현으로 세지 않는다.
- 같은 복구 시험: 동일 Java JAR, 완료 문서 4건·중단 Job 1건·손실 관측 60건, 목표 11초 간격, 300초 외부 전송 구간 2회. 수신 대기·전송 때문에 달라진 실제 간격은 그대로 기록한다.

```text
그림 3 — 복구 회차의 합격 범위와 원복 [설계]

마지막 보존 완료 구간의 성공 응답 원장
  → 필요한 WAL·원본 generation 고정
  → 원본 데이터 추가 취득 중단
  → 새 PGDATA·실제 OpenSQL 복원
  → Worker·Flyway·수선 전 최초 감사
       ├─ 완료 구간의 요청 누락: 최신성 보완 검증 미달
       └─ 누락 0: 복원 DB 활성화 허용
  → 기존 기능·Job 재개·새 업로드·최종 정합성 확인
  → 원래 3노드·설정·소유 자원 정리

보존 완료 뒤 추가된 요청은 별도 손실 관측으로 남긴다.
최종 입력을 뒤늦게 보충해 손실 0건을 만들지 않는다.
```

이 재시험은 격리 복원 기능과 해당 구간의 손실 측정이다. 공개 서비스 전환·전체 사이트 소실·Ollama 생성 답변·운영 RPO 0을 주장하지 않는다. 실패·중단·재시도는 새 run ID와 별도 원장으로 보존한다.
