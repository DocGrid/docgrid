# 저장소 고아 Object 탐지와 안전한 회수 설계

> 이슈 번호가 정해지면 연결한다. 이 문서는 단계별 설계를 설명하며, 1단계 읽기 전용 탐지가 구현되었다.
> 실행 결과와 측정값은 `docs/test-results/`에 따로 기록한다.

## 1. 배경

파일 저장소 쓰기와 DB 트랜잭션은 원자적으로 묶이지 않는다. 최초 문서 및 새 버전 업로드는 파일을 검증하고 해시를 계산한 뒤, 재사용할 `FileObject`가 없으면 저장소에 후보 Object를 먼저 쓴다. 이후 DB 트랜잭션에서 후보를 점유하거나 기존 `FileObject`를 재사용한다. DB 실패 또는 중복 업로드 경합 패배 시 두 업로드 Facade가 미사용 후보를 보상 삭제한다. 자세한 기존 흐름은 `docs/design/gimin-#25-document-version-upload.md` 13장에 있다.

`cleanupCandidate()`는 삭제 실패를 로그로만 남기는 최선 노력 작업이다. 저장소 삭제 자체가 실패하거나, 파일 저장 뒤 보상 삭제 전에 프로세스가 종료되거나, 네트워크 단절로 삭제 결과를 알 수 없으면 DB가 참조하지 않는 Object가 남을 수 있다. 이런 Object는 이미 커밋된 DB 참조가 가리키는 파일 누락과 다르다. 현재 서비스 요청에는 영향을 주지 않지만 저장 공간·비용이 누적되고 필요 없는 원본 바이너리가 남는다. 발생 빈도와 누적량은 아직 측정되지 않았으므로 드물다고 단정하지 않는다.

현재 `FileStorageService`는 `store`·`read`·`delete`만 제공한다. 저장소 삭제 호출처는 두 업로드 Facade의 `cleanupCandidate()`뿐이다. `SyncOrphanInspector`는 DB의 고아 Chunk·Embedding 행을 검사할 뿐 저장소 Object는 검사하지 않는다. 보상 삭제 실패 전용 메트릭이나 경보도 없다. `docs/test-results/gimin-#27-minio-concurrency-integration-test.md` 11장 역시 기존 고아 Object 탐지를 후속 과제로 기록한다.

## 2. 목표와 범위

첫 배포의 목표는 **탐지**다. 현재 활성 저장소의 오래된 문서 Object와 `file_objects` 행을 비교해 고아 후보의 개수·용량을 측정한다. `DRY_RUN`에서는 저장소를 삭제하거나 업로드 흐름을 바꾸지 않는다. 검사 실패와 측정값의 노후화도 관측한다.

자동 **회수**는 별도 배포에서 추가한다. 업로드 후보를 저장 전에 DB에 등록하고, 업로드와 GC가 같은 후보를 두고 경쟁할 때 어느 쪽이 점유했는지 DB 상태 전이로 확정한 뒤에만 삭제한다. 자동 삭제가 켜진 환경의 모든 DocGrid 업로드 경로가 이 규칙을 사용해야 한다.

다음은 이 GC의 범위가 아니다.

- 문서 soft delete 시 원본 삭제: 현재 문서 삭제는 원본과 버전 이력을 보존한다. `FileObject` 행이 있는 파일은 문서 상태와 관계없이 남긴다. 보존 기간 정책은 별도 문제다.
- `FileObject` 행은 있지만 연결된 `DocumentVersion`이 없는 DB 데이터 정리: 정상 업로드는 둘을 같은 트랜잭션에 만들지만, 과거 데이터나 수동 복구까지 없다고 단정할 수 없다. 이 GC는 `FileObject` 행이 있으면 보존한다.
- 현재 활성 Provider·Bucket 밖에 있는 이전 저장소의 Object, 저장소 버전 관리의 비현재 버전, Local 저장소의 `.docgrid-*.tmp` 임시 파일 정리.
- 키 형식이 다르거나 DocGrid 소유임을 확인할 수 없는 Object의 자동 삭제. 해당 객체는 제외 수량으로 관측하고 별도 조사한다.

## 3. 고아 **후보**의 정의

탐지 단계에서는 아래 조건을 모두 만족할 때 고아 **후보**라고 부른다. DB 행이 없다는 관찰만으로 자동 삭제 가능한 Object라고 부르지 않는다.

| 조건 | 기준 |
| --- | --- |
| 위치 | 현재 활성 Provider·Bucket의 `documents/` 접두사 아래 |
| 키 | 현재 업로드 코드가 생성하는 `documents/{UUID}/{UUID}.{확장자}` 형태 |
| 형식 | 두 UUID는 소문자 표준 표기이며 확장자는 현재 허용된 `txt`, `md`, `pdf`, `docx` 중 하나 |
| 시간 | 저장소의 Last-Modified가 존재하고 `now - Last-Modified >= grace-period` |
| DB 참조 | `file_objects`에 동일한 `(storage_provider, bucket_name, object_key)` 행이 없음 |

정규식 원문에서 점은 `\.`으로 쓴다. Java 문자열 리터럴에서는 백슬래시를 한 번 더 이스케이프해 `"\\."`로 쓴다. 두 업로드 Facade의 추적 가능한 Git 이력에서는 위 키 형태를 사용했고, `FileValidationService`는 확장자를 소문자로 정규화한다. 이는 실제 버킷의 모든 과거·수동 생성 Object까지 증명하지 않는다. 형식이 맞지 않는 객체와 수정 시각을 확인할 수 없는 객체는 자동 삭제에서 제외한다.

```text
^documents/[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}/[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}\.(?:txt|md|pdf|docx)$
```

`FileObject` 존재 여부가 이 작업의 참조 기준이다. 한 `FileObject`를 여러 `DocumentVersion`이 재사용할 수 있으므로 문서나 버전의 개수를 기준으로 물리 파일을 지우지 않는다. `file_objects`에는 위 위치 조합의 유일 제약이 있어 일괄 조회에 사용할 수 있다.

## 4. 삭제 안전성 불변 조건

1. `FileObject` 행이 있거나 업로드 후보 원장의 상태가 `CLAIMED`이면 GC는 삭제하지 않는다.
2. 업로드는 후보 원장 행을 점유하기 **전**에 `FileObject`를 삽입하지 않는다. 후보 점유와 `FileObject`·`DocumentVersion` 생성은 한 DB 트랜잭션에서 커밋되거나 함께 롤백된다.
3. GC가 후보를 `RECLAIMING`으로 선점하면 그 후보를 사용한 업로드 트랜잭션은 커밋할 수 없다. 업로드가 먼저 `CLAIMED`로 커밋하면 GC는 선점할 수 없다.
4. 저장소 목록 조회 또는 DB 조회가 실패하거나 검사가 중간에 끝나면 그 회차에서 삭제하지 않고, 부분 집계를 정상적인 전체 집계로 게시하지 않는다.
5. 저장소 삭제 성공 여부가 불확실하면 정리 완료로 표시하지 않는다. 다음 검사에서 재확인·재시도한다.

유예 시간과 삭제 직전 DB 재조회는 필요하지만 **2·3번을 대체하지 못한다**. 후보를 저장한 뒤 DB 트랜잭션이 유예 시간보다 오래 대기할 수 있다. 그때 GC가 행 부재만 보고 지운 직후 업로드가 커밋하면 DB가 없는 파일을 참조한다. 후보 원장의 조건부 상태 전이가 이 경합을 막는다. PostgreSQL은 같은 행에 대한 동시 갱신과 잠금을 트랜잭션 종료까지 조정한다. [PostgreSQL 행 잠금 설명](https://www.postgresql.org/docs/current/explicit-locking.html).

이 보장은 **원장을 사용하는 DocGrid 업로드 경로**에 대한 것이다. DB 또는 저장소를 외부에서 수동으로 변경하는 작업, 서로 다른 Endpoint·Local Root를 바라보는 프로세스까지 자동으로 통제하지 않는다. 삭제 모드를 켜기 전에 같은 DB를 사용하는 업로더와 GC가 같은 물리 저장소를 바라보는지 확인해야 한다.

## 5. 탐지 작업

### 5.1 저장소 목록 조회

`FileStorageService`에 문서 접두사의 Object를 페이지 또는 스트림 단위로 조회하는 기능을 추가한다. 결과에는 Provider·Bucket·Key, 크기, Last-Modified가 포함된다. MinIO는 `listObjects`, S3는 `ListObjectsV2` 페이지 조회를 사용하고 Local은 설정 Root 아래를 경로 검증과 함께 순회한다. 전체 Object를 한 번에 메모리에 적재하지 않는다. [MinIO Java 목록 API](https://docs.min.io/aistor/developers/sdk/java/api/), [S3 ListObjectsV2](https://docs.aws.amazon.com/AmazonS3/latest/API/API_ListObjectsV2.html).

접두사와 키 형태를 모두 확인한다. Local 순회에서는 심볼릭 링크와 Root 밖 경로를 따라가지 않으며 `.docgrid-*.tmp`는 별도 제외 집계로 처리한다. 목록 응답에 크기·수정 시각이 없거나 값이 잘못된 항목은 삭제 후보로 승격하지 않는다.

### 5.2 DB 일괄 비교

목록 한 페이지의 유효한 Object Key를 모아 `FileObjectRepository`에서 Provider·Bucket·`object_key IN (...)` 조건으로 **키만 projection**해 읽는다. 현재 유일 제약을 활용하므로 탐지 때문에 새 DB 인덱스를 추가하지 않는다. Object 하나마다 DB 조회를 실행하지 않는다.

전체 접두사 순회를 성공적으로 마친 때에만 고아 후보 수·용량·제외 수량과 검사 시각을 새로운 Snapshot으로 게시한다. 목록이나 DB 조회가 실패하면 이전 성공 Snapshot을 보존하고 실패 횟수를 올린다. 1단계는 별도의 실행 모드를 노출하지 않는 읽기 전용 탐지이며 물리 삭제 코드가 없다.

## 6. 자동 회수를 위한 후보 원장

### 6.1 등록과 업로드 점유

별도 배포에서 `storage_upload_candidates` 테이블을 도입한다. `(storage_provider, bucket_name, object_key)`를 유일하게 두고 `REGISTERED`, `CLAIMED`, `UNUSED`, `RECLAIMING`, `CLEANED` 상태와 생성·마지막 정리 시각을 기록한다. GC 시도에는 별도의 `cleanup_token`과 만료 시각을 기록해 한 번에 한 실행자만 삭제를 시도하게 한다.

최초 문서와 새 버전 Facade가 새 Object Key를 생성하면, 저장소에 쓰기 **전에** 짧은 DB 트랜잭션으로 `REGISTERED` 행을 커밋한다. 등록 실패 시 저장소에 쓰지 않는다. 이미 존재하는 `FileObject` 재사용 경로에는 후보를 만들지 않는다. 저장소 요청이 실패하더라도 서버에 Object가 생성됐을 가능성이 있으므로 등록 행은 후속 검사 근거로 남긴다.

이후 기존 업로드 DB 트랜잭션은 `FileObject` 삽입 전에 후보 행을 잠그고 `REGISTERED` 상태를 확인한다. 새 `FileObject`가 후보 Key를 점유하면 `CLAIMED`, 중복 해시 경합에서 기존 `FileObject`를 재사용하면 `UNUSED`로 바꾼다. 상태 변경, `FileObject` 삽입, `DocumentVersion`·Job 생성은 같은 트랜잭션에 속한다. 트랜잭션 실패 시 상태 변경도 롤백되어 `REGISTERED`로 남는다. Facade의 즉시 보상 삭제는 유지하고, 삭제가 성공한 뒤에만 `CLEANED`로 표시한다.

### 6.2 GC 선점과 삭제

성공한 전체 목록 검사 뒤 GC는 등록 시각부터 충분히 오래된 `REGISTERED`·`UNUSED`·`RECLAIMING` 후보 원장 행을 별도 페이지로 읽는다. 위치와 Key 형식을 검증하고 `FileObject`가 없으면 조건부 갱신으로 `RECLAIMING`에 선점하면서 새 `cleanup_token`과 Lease 만료 시각을 기록한다. 이미 `RECLAIMING`이면 이전 Lease가 만료된 경우에만 새 실행자가 선점한다. 선점 트랜잭션을 커밋한 뒤 `FileObject`를 재확인하고 저장소에 멱등 삭제를 요청한다. 실제 Object가 없던 등록 행도 이 방식으로 정리된다. 삭제 성공 또는 Object 부재를 확인하면 자기 Token으로만 `CLEANED`로 표시한다. 저장소 오류나 타임아웃이면 `RECLAIMING`을 유지해 Lease 만료 뒤 다음 회차에서 재시도한다. `CLAIMED` 상태이거나 선점 갱신 결과가 0인 Key는 삭제하지 않는다. `CLAIMED` 행은 대응하는 `FileObject` 커밋을 확인한 뒤 보존 기간에 따라 원장만 정리할 수 있다.

```text
업로드가 후보 행을 먼저 잠금 → FileObject와 CLAIMED 함께 커밋 → GC 선점 실패 → 파일 보존
GC가 RECLAIMING 먼저 커밋 → 업로드의 REGISTERED 확인 실패 → 업로드 DB 롤백 → GC 삭제
```

GC가 저장소 쓰기 중인 후보를 선점하면 해당 업로드는 실패할 수 있지만, 삭제된 파일을 DB가 참조한 채 성공할 수는 없다. 이런 불필요한 업로드 실패를 줄이기 위해 삭제 유예 시간은 업로드 요청·저장소 쓰기의 **강제된 최대 소요 시간보다 충분히 길게** 설정한다. 최대 시간이 정해지지 않은 환경에서는 `DELETE` 모드를 활성화하지 않는다. 저장소 쓰기가 GC 삭제 뒤 늦게 완료된 경우에도 업로드는 `RECLAIMING` 또는 `CLEANED` 후보를 점유할 수 없다. `CLEANED` 상태인데 Object가 다시 보이면 유예 시간 경과 후 `RECLAIMING`으로 재선점해 삭제한다. 정리된 후보 원장은 늦은 쓰기의 최대 가능 시간이 지난 뒤에만 폐기한다.

후보 원장이 없는 오래된 Object는 초기 자동 삭제 대상이 아니다. 탐지 결과를 검토하고, 원장 도입 전 업로드 인스턴스가 모두 종료됐으며 유예 시간이 지난 뒤 별도의 일회성 정리 대상으로 승인한다. 롤링 배포 중 옛 코드가 만든 후보를 자동 삭제하지 않는다.

## 7. 실행 설정과 다중 인스턴스

1단계 설정 기본값은 `storage.orphan-gc.enabled=false`, 최초 지연 `1m`, 검사 주기 `24h`, 페이지 크기 `500`, 유예 시간 `72h`다. 수치는 초안이며 실제 업로드 최대 시간과 저장소 규모를 측정해 조정한다. 삭제 기능이 없으므로 `mode`나 삭제 수량 설정도 아직 노출하지 않는다. 후속 `DELETE` 모드는 후보 원장 배포·최대 업로드 시간 설정·동일 저장소 배포 확인 뒤에만 추가할 수 있다. 한 번의 삭제 수량 상한도 설정해 급격한 저장소 변경을 막되, 스캔 자체는 접두사 전체를 끝까지 순회한다.

1단계는 `@Scheduled`와 인스턴스 내부 `AtomicBoolean`으로 같은 프로세스의 겹친 실행만 막는다. 여러 인스턴스가 동시에 검사할 수 있지만 저장소와 DB를 읽기만 하므로 정합성은 깨지지 않는다. 다만 목록·DB 부하와 인스턴스별 Gauge 해석이 중복될 수 있으므로 운영에서는 한 인스턴스만 활성화하는 구성을 권장한다. 자동 삭제 단계에서는 PostgreSQL의 세션 단위 advisory lock 또는 동등한 분산 실행 제어를 추가해 한 인스턴스만 전체 순회를 맡게 한다. 후보 Key별 조건부 상태 전이는 락 설정 오류로 두 GC가 동시에 실행되더라도 한쪽만 삭제를 점유하게 하는 추가 방어선이다.

## 8. Metric과 경보

1단계는 Micrometer에 마지막 **성공한 전체 검사**의 스캔·참조·고아 후보·최근 제외·유효성 제외 Object 수와 후보 용량을 Gauge로 노출한다. 검사 성공·실패는 고정된 `outcome` 태그의 Counter로 기록한다. 실패 회차가 이전 정상 수치를 0으로 덮지 않도록 Snapshot의 나이도 노출한다. Object Key, 파일명, 사용자 ID는 Metric 태그나 공개 오류 메시지에 넣지 않는다.

Prometheus 규칙은 기본 24시간 주기를 기준으로 검사 실패와 30시간 이상 갱신되지 않은 Snapshot을 감지한다. 고아 후보 수·용량 자체의 경보 임계값은 첫 운영 측정 전 임의로 정하지 않는다. 삭제 실패 Counter와 경보, 기존 `cleanupCandidate()` 실패 Counter는 삭제 단계에서 추가해 GC 도입 전후의 실패 경로를 비교한다. Alertmanager 수신 채널은 기존 운영 설정에 따른다.

## 9. 장애와 제외 조건

| 상황 | 처리 |
| --- | --- |
| 저장소 목록 조회 또는 DB 조회 실패 | 검사 실패 기록; 부분 집계 미게시; 삭제 중단 |
| 수정 시각 없음·Key 형식 불일치 | 제외 집계; 자동 삭제 금지 |
| `FileObject` 존재 또는 후보 상태 `CLAIMED` | 보존 |
| GC 선점 중 업로드가 먼저 후보 점유 | 조건부 갱신 실패; 보존 |
| 업로드 중 GC가 먼저 선점 | 업로드 DB 트랜잭션 실패; 후보 재검사·정리 |
| 저장소 삭제 실패 또는 결과 불명 | 완료 표시 금지; 다음 검사에서 재시도 |
| 후보 원장 없음 | `DRY_RUN` 관측 및 수동 검토; 초기 자동 삭제 금지 |
| 다른 Provider·Bucket·Endpoint·Local Root | 검사 범위 밖이거나 배포 설정 오류; 자동 삭제 금지 |

버전 관리가 켜진 Bucket에서는 현재 어댑터처럼 버전 ID 없이 삭제하면 비현재 버전이 남을 수 있다. 따라서 첫 `DELETE` 모드는 버전 관리가 없는 Bucket만 지원하고, 버전 관리 환경에서는 `DRY_RUN`으로 제한한다. 비현재 버전 회수와 보존 규칙은 별도 설계가 필요하다. [S3 버전 삭제 설명](https://docs.aws.amazon.com/AmazonS3/latest/userguide/DeletingObjectVersions.html).

## 10. 검증과 배포 순서

**탐지 작업**에서는 Local·MinIO·S3 목록 Adapter의 접두사·페이지·Metadata 변환을 단위 검증한다. 탐지 Service에는 오래된 미참조 Object, 최근 후보, DB 참조 Object, 형태가 다른 Key와 수정 시각 누락을 준비해 개수·용량과 Bulk Query 묶음을 확인한다. 저장소 `delete()`가 호출되지 않고, 목록·DB 오류 때 부분 결과가 정상 Snapshot을 덮지 않아야 한다. 실제 MinIO·S3 통합 측정은 기존 동시 업로드 테스트의 버킷 격리 방식을 활용하는 후속 검증으로 남긴다.

**후보 원장 작업**에서는 두 업로드 Facade의 정상 업로드·기존 `FileObject` 재사용·중복 해시 경합·DB 롤백·저장소 요청 오류를 회귀 검증한다. 업로드 트랜잭션과 GC 상태 전이를 테스트 장벽으로 멈춰 각각 먼저 이기는 경우를 재현하고, 커밋된 `FileObject`가 삭제된 Object를 가리키는 결과가 나오지 않는지 확인한다.

**삭제 작업**에서는 프로세스가 파일 저장 뒤 DB 기록 전에 종료된 상황, 보상 삭제 실패, 삭제 결과 불명, 재시도를 재현한다. 참조 중인 파일과 soft delete된 문서의 파일은 그대로 남아야 한다. 두 GC 인스턴스가 동시에 시작해도 한 번만 순회·선점하는지 확인한다. 버전 관리 Bucket과 원장 없는 역사적 후보가 자동 삭제에서 제외되는지도 검사한다.

배포는 `DRY_RUN` 측정 → 원장을 쓰는 모든 업로드 인스턴스 배포 → 옛 인스턴스 종료와 유예 시간 경과 확인 → 제한된 `DELETE` 활성화 순서다. 실제 측정값과 테스트 실행 방법은 `docs/test-results/`에 기록한다. 포트폴리오에는 측정 전후의 고아 Object 수·용량, 스캔 시간·목록 요청 수·DB 조회 수, 장애 재시도 결과와 정상 파일 오삭제 0건의 검증 조건을 함께 제시한다. 실측 전에는 발생 빈도나 회수량을 숫자로 주장하지 않는다.
