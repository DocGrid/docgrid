# 업로드 복원 판정 계약 검증 — 2026-10-18

## 목적

업로드 응답 원장을 복원 DB·원본과 대조하고, 최초 상태 감사 전에 Worker가 켜지지 않는지 검증한다. 이번 기록은 로컬 Python의 합성 JSON·제어 자식 프로세스 시험이다. 실제 OpenSQL·GCS·BGE-M3 복구를 실행한 결과가 아니다.

## 테스트 환경

- 기반 리비전: `4cfe9666ac3a670bb72c8cd4d933bc7d7238fce0`와 이 PR의 계약 코드.
- 명령: `python3 -m unittest discover -s scripts/opensql -p test_dr_recovery.py -v`
- 외부 서비스: DB·Docker·GCP·모델 사용 안 함. 제어 연산자는 합성 JSON을 반환하는 로컬 Python 자식 프로세스.
- 원래 개인 환경 파일과 공개 서비스 설정 수정 없음. 파일 경로는 공개 로그 저장 전에 마스킹했다.

## 테스트 방법

정상·불명 HTTP 결과, 중간 성공 응답 유실, DB 관계 불일치, 보존 객체 누락·해시·generation 불일치, 최초 감사 순서, 정리 누락을 각각 주입했다. 합격 기준은 판정 계약 전체 통과, 감사 미통과 시 activate 미호출, 정리 실패 시 PASS 금지다.

- 고정 보존 객체 generation과 다른 객체는 해시가 같아도 최초 감사가 기동을 허용하지 않는다.
- 정리 명령 누락·잘못된 후속 명령은 복원 시작 전에 거부한다. 정리 실패와 실행 중단은 INCOMPLETE다.

## 검증 과정에서 확인된 사항

첫 회차에서 자식 파일을 `operator.py`로 만든 것이 Python 표준 `operator` 모듈을 가렸다. `functools` import 순환 때문에 연산자 실행 5개가 실패·오류로 끝났다. 파일명을 `controlled_driver.py`로 바꾼 뒤 R2를 별도 실행했다. R3는 복원 입력 해시·민감 필드·보존 객체 버전 조건을 보강한 별도 회차다. R4는 최종 감사에서도 원본 접근을 금지하고, 거부된 기능 응답이 결과 파일에 남지 않으며 감사 뒤 늦은 응답이 합격 판정에 섞이지 않는지 검증했다.

제어기가 받는 `source_access_used=false` 등은 연산자 확인값이다. 이 단위 시험은 실제 VM의 원본 접근 차단, 실제 WAL 연속성, OpenSQL 라이선스 복원 가능성, 검색 품질, 실제 복구 시간, RPO 또는 공개 서비스 전환을 증명하지 않는다. 후속 실험에서 각 조건과 연산자를 실제로 검증해야 한다.

설계와 실제 실행은 [업로드 복원 판정 설계](../../design/issue-560-upload-recovery-contract.md)에서 구분한다. 초기 유실 집계와 최종 기능 수렴이 서로 다른 기록이라는 점을 유지한다.
