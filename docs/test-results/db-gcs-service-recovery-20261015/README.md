# OpenSQL·GCS 격리 서비스 복구 시험 — 2026-10-15

## 판정

이전 [DB·GCS 시점 복원 시험](https://github.com/DocGrid/docgrid/pull/500)에서 만든 **격리 복원 DB와 독립 GCS 사본**에 로컬 백엔드를 연결했다. 기존 문서 다운로드, 합성 문서 업로드·다운로드, 검색 API, 제한된 Worker의 Job 처리를 확인했다. **실제 BGE-M3와 Ollama를 통한 의미 검색·답변은 검증하지 않았다.** 검색과 인덱싱은 1,024차원 고정 벡터 스텁을 사용했다.

## 실행 경계

```text
기존 클러스터(리더 1·Standby 2) ── 백업·WAL ──▶ 백업 VM
                                    │
                             이전 PITR 사본
                                    ▼
                       Standby 호스트의 별도 PGDATA
                         localhost 전용 OpenSQL
                                    │
                         IAP 터널 + 로컬 백엔드
                                    │
              독립 GCS 복원 버킷 ◀── 파일 참조 91건 변경
                                    │
            합성 업로드·다운로드·검색·제한 Worker만 실행
```

원래 Standby를 잠시 제외하는 동안 자동 원복 타이머를 두었다. 타이머가 격리 DB를 종료한 뒤 기존 Standby를 재합류시켰다. 첫 회차에서 이 타이머가 Worker 판정보다 먼저 실행되어 해당 경로는 미검증으로 남겼다. 두 번째 회차에서도 타이머가 실행된 뒤 클러스터 복귀를 확인했다.

## 결과 해석과 다음 단계

1. **서비스 경로 일부 복구**: DB·GCS 복원본으로 다운로드와 새 업로드가 되었고, 고정 벡터 스텁 조건에서는 검색·인덱싱이 작동했다.
2. **모델 의존 경계**: 실제 BGE-M3/Ollama 서버가 없어 의미 검색 품질, 답변 완료, 실제 모델 장애 후 복구는 이 시험 결과로 주장할 수 없다.
3. **시간 측정 경계**: 복원 시작부터 모든 사용자 기능이 준비되기까지의 단일 RTO는 측정하지 않았다. 중간에 앱 재시작, 시험 스텁 수정, 수동 Job 재시도가 있었다.
4. **남은 시험**: 실제 모델을 격리 연결한 뒤 미완료 Job의 Worker 중단·Lease 만료·재획득, 인덱싱과 검색·답변, 새 업로드를 한 회차에서 측정한다. 그 전에는 “전체 서비스 복구”로 표기하지 않는다.

기록은 시험 중 민감 식별자·토큰·문서 내용을 수집하지 않은 안전한 상태값과 수치만 포함한다. 시험용 GCS 객체 2개(68·129바이트)는 generation 조건으로 제거해 독립 복원 버킷을 원래 92객체로 되돌렸다.
