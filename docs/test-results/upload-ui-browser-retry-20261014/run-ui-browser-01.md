# UI-BROWSER-20261014-01 — 최초 업로드 화면의 동일 키 재시도

**사후 판정 정정:** 최초 기록의 “문서·버전·파일·Job 각각 1건 확인”은 모의 API의 동일 메모리 항목 수를 네 필드로 표시한 값이었다. 아래 결과는 브라우저의 동일 키 재시도와 논리 업로드 시도 1건까지만 검증한 것으로 판정 범위를 바로잡았다. 시험을 다시 실행한 기록은 아니다.

- **목적:** 최초 문서 업로드가 서버에서 저장된 뒤 HTTP 502를 받았을 때, 브라우저 화면이 저장 여부 불명을 표시하고 같은 키·파일·입력으로 재시도하는지 확인한다.
- **실행 위치:** 로컬 브라우저의 실제 DocGrid 프론트엔드(`develop` 기준 `894ad4242f35a3cbb3f5d5dc458c6ed048786e0d`)와 루프백 모의 API. GCP, OpenSQL, GCS, Vercel은 이 실행에 참여하지 않았다.
- **원장 보존 시각:** 2026-10-14 02:14:23 KST. 모의 API 원장의 각 요청에는 개별 시각이 없어 요청 순서만 기록했다.
- **합성 입력:** `fixture.txt` 107바이트, 제목 `docgrid-upload-browser-fixture`, 설명 없음, 공개 범위 `PRIVATE`. 시험용 로그인 값은 모의 API가 저장하지 않았다.
- **실행 방법:** `BACKEND_API_URL=http://127.0.0.1:18761 npm run dev -- --host 127.0.0.1 --port 18760`을 `frontend/`에서 실행하고, `node mock-server.mjs`로 모의 API를 실행했다. 저장소 루트에서 재현할 때는 `node docs/test-results/upload-ui-browser-retry-20261014/mock-server.mjs`를 사용한다. 브라우저에서 로그인 → 문서 목록 → 문서 업로드 → 합성 파일 선택 → 업로드 시작 → 같은 업로드 다시 시도 순으로 조작했다.
- **성공 기준:** 첫 요청은 모의 저장 1건 뒤 502, 화면은 저장 여부 불명 안내와 재시도 버튼을 표시하고 파일·제목·설명·공개 범위를 잠근다. 두 번째 요청은 첫 요청과 동일 키·논리 본문으로 201을 받는다. 모의 API의 논리 업로드 시도와 화면의 문서 표시는 각각 1건이어야 한다.

## 해석과 한계

실제 브라우저 조작과 프론트엔드 프록시를 통과한 두 POST의 키·논리 입력이 같았다. 화면의 재시도 경로가 새 키를 만들지 않는다는 점을 확인했다. 모의 API의 `documentCount`·`versionCount`·`fileCount`·`jobCount`는 모두 동일한 메모리 항목 수에서 계산하므로, 네 저장 대상을 독립적으로 검증한 결과가 아니다. 실제 OpenSQL·GCS의 저장 건수도 뜻하지 않는다. 첫 실패는 HTTP 502 응답으로 재현했으며 브라우저가 응답을 전혀 읽지 못하는 연결 종료 시나리오는 이번 실행에 포함하지 않았다. Vercel 배포 버전과 전체 클라우드 경로의 UI 동작도 이 결과로 보증할 수 없다. 앞선 GCP 직접 API 시험과 별도 결과로 취급한다.

## 정리

시험용 서버는 루프백에서만 실행했고, 외부 서비스나 실제 사용자 문서를 사용하지 않았다. 원장에는 원래 요청 키, 인증 토큰, 비밀번호, 파일 본문을 기록하지 않았다. 시험 종료 뒤 프론트엔드와 모의 API를 모두 중지했고, 두 루프백 포트의 연결 거부를 확인했다. 개발 서버에는 검색 화면이 부가로 호출한 컬렉션·대화 목록 API의 404가 각 1회 있었다. 모의 API에서 해당 기능을 구현하지 않아 발생했으며 업로드 2회에는 영향을 주지 않았다.
