# k6 미전송·VU·응답 대기·부하 VM 자원 1초 계측

- 관련 이슈: [#405](https://github.com/DocGrid/docgrid/issues/405)
- 실행일: 2026-10-04 KST (원본 시각은 UTC)
- 범위: **부하 발생기 VM 한 대 내부**. 이번 진단에서는 앱·OpenProxy·OpenSQL에 요청하거나 primary 장애를 주입하지 않았다.
- 목적: 이전 계획 이전 실행 `ha405sw002/003`에서 각각 발생한 381/167건의 미전송을 다음 장애 재시험에서 원인별로 분석할 수 있도록, k6와 부하 VM의 원본 숫자를 같은 UTC 초에 남긴다.

## 수집·판정 방법

```text
k6 constant-arrival-rate (목표 요청 슬롯)
  ├─ 전송 성공 시점 → http_reqs / 응답 대기 / 반복 시간 Point
  ├─ 슬롯에 쓸 VU가 없으면 → dropped_iterations Point (HTTP 전송 없음)
  └─ 매초 VU gauge → 활성 VU / 확보 VU
                         │
부하 VM /proc/stat, /proc/meminfo, /proc/<k6 PID>/{stat,status}
  └─ 매초 호스트 CPU·가용 메모리·k6 CPU/RSS/스레드
                         │
                UTC 초 단위 결합 → 계측-1초.csv
```

요청 URL·내부 주소·토큰·오류 문자열이 JSON 지표에 기록되지 않도록 k6 시스템 태그를 비활성화했다. VM 표본기는 숫자형 `/proc` 필드만 읽고 k6의 환경변수·명령행은 읽지 않는다. 원시 k6 stderr는 기록 전에 신뢰할 수 있게 비식별화할 수 없어 수집하지 않는다. 각 실행의 원본 지표·이벤트·VM 표본·집계는 서로 다른 0700 실행 디렉터리에 보관한다. 전체 원본 디렉터리는 공개 저장소로 반출하지 않았다.

원본 Point의 건수를 k6 전체 요약과 대조하고, VU Point 존재 여부와 VM 표본 2개 이상을 검사한다. 불일치하면 1초 결과를 성공으로 보고하지 않는다. **한 UTC 초의 VU·자원 표본과 HTTP 완료 시각은 정확한 인과 순서가 아니다.** VU는 주기적 gauge이므로 아주 짧은 요청에서는 같은 초의 활성 VU가 0으로 보일 수 있다. HTTP 응답 대기는 요청 완료 시각의 초에 놓인다.

두 loopback 실행의 HTTP 성공/실패는 OpenSQL 정합성 판정이 아니다. 빠른 경로는 미사용 경로의 404, 지연 경로는 시험 응답기의 201이다. `ha405diagvm02/03/04` 모두 계측기의 건수 대조·VU Point·VM 표본 검사를 통과했다. k6 종료 코드 99는 각각 HTTP 실패 또는 미전송 임계값 때문이며, 집계기 실패와 구분한다.

```text
8초 지연 대조군: 목표 70 슬롯/초 · 처음 VU 40 · 상한 VU 160

시작 ── VU 증설 중 ── VU 160 도달 ── 30초 목표 발행 종료 ── 진행 요청 종료
          │                │
          ├─ 같은 초에 확보 VU가 160 미만인 미전송 168건
          ├─ VU 표본 없는 첫 초의 미전송 9건
          └─ 확보 VU 160이 관측된 초의 미전송 1,284건

합계 1,461건. 분류는 '같은 UTC 초의 gauge와 event'를 비교한 것이며
요청별 VU 확보 실패의 정확한 발생 순서를 증명하지 않는다.
```

첫 미전송 초는 2026-10-03 15:46:49 UTC이며 그 초에는 VU gauge가 없었다. 15:46:50 UTC에는 미전송 35건과 확보·활성 VU 53, 호스트 CPU 9.0%가 같은 초에 기록됐다. 15:46:54 UTC부터는 VU 160/160과 미전송 70건/초가 관측됐다. 이는 합성 시험에서 **초기 VU 40에서의 증설 지연**과 **최종 VU 160 상한**을 분리해 볼 실마리다. 초별 표본만으로 첫 9건의 직접 원인을 단정하지 않는다.

로컬 구문 검사 첫 시도 `ha405-telemetry-local-02`는 worktree 쓰기 제한 때문에 `py_compile` 캐시 생성에 실패했고, 재실행 `-02b`에서 캐시를 별도 임시 위치로 두어 통과했다. 이 실패도 테스트 코드 실패로 숨기지 않는다.

**아직 결론낼 수 없는 것:** 앞선 실제 switchover 실행 `ha405sw002`의 381건과 `ha405sw003`의 167건은 이번 계측 코드 배포 **전**에 발생했다. 당시 매초 dropped/VU/VM 자원 Point가 없어 합성 시험 결과를 실제 장애의 원인으로 소급할 수 없다. 다음 실제 장애 재시험에서 같은 실행 ID의 `계측-1초.csv`와 독립 요청 원장을 함께 얻고, 201 누락·중복과 미전송을 별도로 판정해야 한다. 이 문서는 **계측기 검증**이지 OpenSQL 장애 원인 확정이나 RTO/RPO 재측정 결과가 아니다.
