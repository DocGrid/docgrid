# 필요한 WAL의 보관·외부 복사 완료 경계 검증

관련 이슈: #563. 앞선 [복구 계측](../dr-functional-recovery-20261018/README.md)은 성공 응답 65건 중 33건만 복원했고, 외부에 동결된 WAL 끝까지만 재생했다. 이번 검증은 그 공백을 만들 수 있는 **고정 대기·명령 종료 코드 기반 완료 판정**을 조사한다. 전체 복구 재시험 결과는 이 문서의 재현 결과와 구분해 별도 기록한다.

## 목적

`pg_switch_wal()` 뒤 2초를 기다리고 `archive-wal` 한 번이 성공하면 최신 WAL까지 보관됐다고 볼 수 있는지 확인한다. 필요한 파일이 실제 보관되기 전에 성공으로 판정하면 외부 원본이 있어도 대응하는 DB 행을 복구하지 못할 수 있다.

## 테스트 환경

| 항목 | 실제 사용·범위 |
| --- | --- |
| DB | 기존 OpenSQL 17.8 클러스터에 소유 마커가 있는 별도 논리 DB·합성 marker 테이블 |
| 수신·보관 | 로컬 Docker의 실제 Barman 3.19.1·PostgreSQL 17 수신 도구, 새 전용 카탈로그·터널 |
| 공개 자원 | 기존 Primary·동기 Standby 설정 변경 없음. 이 재현에서는 복원용 노드 중단 없음 |
| 단위 시험 | 로컬 Python, 제어한 파일·시계·명령 대역. 실제 클라우드 시험과 구분 |
| 외부 복사 | 아래 LIVE2는 **로컬 Barman 보관 완료**까지 검증. 실제 GCS 재읽기는 별도 통합 복구 회차에서 검증 |
| 개인 파일 | 기존 `.env`·프런트엔드 개인 설정 변경 없음 |

## 테스트 방법

1. 각 run ID의 목적·위치·성공 기준을 먼저 저장했다. 명령 출력은 메모리에서 처리하고 공개 기록에는 파일명·시각·종료 코드·카운터만 남겼다.
2. 설치 이미지에서 네트워크 없이 `inspect.getsource(StreamingWalArchiver.get_next_batch)`로 보류 조건을 읽었다. [동일 버전의 공식 소스](https://github.com/EnterpriseDB/barman/blob/release/3.19.1/barman/wal_archiver.py)와 대조했다.
3. 실제 marker를 커밋하고 WAL을 전환했다. 기존 방식인 2초 대기·archive 1회의 종료 코드와 정확한 대상 파일의 위치를 각각 기록했다.
4. 첫 사례에서는 명시적인 다음 쓰기 없이 최대 20초 동안 필요한 파일을 기다렸다. 이후 각 사례에서 다음 구간의 합성 `pg_create_restore_point`를 생성하고 이름 기반 완료 대기를 실행했다.
5. 소유한 DB·두 역할·수집기·터널·키를 정리했다. 원래 클러스터와 공개 Patroni 설정의 보존을 확인했다.

```text
그림 1 — 명령 성공과 보관 완료의 차이 [실제 관측]

시험 호출자: marker 커밋 → pg_switch_wal → 대상 이름 확보
  │
  ├─ 2초 후 archive-wal → 종료 코드 0 (3/3)
  │    ├─ 사례 1·3: 대상 파일은 streaming에 남음
  │    │            wals 보관 디렉터리에는 없음
  │    └─ 사례 2: 다음 .partial 존재 → 대상 보관 완료
  │
  └─ 따라서 종료 코드만으로 최신성 완료를 판정하면
       이번 3회 중 2회에서 실제 파일 상태와 어긋남
```

코드 0은 명령이 정상 실행됐다는 관측이다. 그 시점에 특정 업무까지 포함하는 WAL 파일이 보관됐다는 증거는 아니었다.

**첫 사례의 추가 대기는 20초 시간 초과가 아니다.** 명시적인 다음 쓰기를 넣지 않아도 **6.966초 뒤 도착**했다. 이후 다음 파일 진행과 이름 확인을 결합한 방식은 3/3 통과했지만, 사례 1·2는 그 전에 이미 보관된 상태이므로 restore point가 모든 사례에 반드시 필요했다는 인과 결론은 내리지 않는다. 백그라운드 WAL 진행의 정확한 발생원도 이번에 계측하지 않았다.

```text
그림 2 — 추가한 완료 계약 [구현]

호출자: 필요한 24자리 WAL 이름 지정
  → wait_for_archived_wal(server, directory, required_wal)
      → archive-wal 반복, 단조 시계 제한 120초(최대 300초)
      ├─ 다른 파일·partial·빈 파일·심볼릭 링크: 완료 아님
      ├─ 오류·제한 초과: 실패, 보존 완료 시각 갱신 안 함
      └─ 정확한 완성 파일: 반환
  → 기존 sync_wals로 복사
  → 원격 같은 파일의 크기·CRC32C 대조
      ├─ 누락·불일치: 실패
      └─ 일치: required_wal_verified=true 기록
```

새 `sync --required-wal <WAL> --wait-timeout 120` 옵션을 쓸 때만 이 계약을 적용한다. 기존 타이머·설정·환경변수는 바꾸지 않았다. 인자 없는 복사의 health는 복사 최근성이고, 업무 최신성이나 RPO 보장이 아니다.

## 검증 과정에서 확인된 사항

- **직접 원인은 시험의 완료 판정 공백이다.** Barman의 수신기 재시작 보호 동작을 제품 결함으로 판단하지 않았다. 수신 중 마지막 파일이 보류된 상태에서 기존 시험이 외부 전송 완료를 추정한 경로를 실제로 재현했다.
- 앞선 32건 전체를 같은 순간의 동일 경합 하나로 소급 확정하지 않는다. 앞선 동결 WAL과 복원 끝 위치가 일치했고, 이번에는 그 입력 최신성이 부족해질 수 있는 구체적인 경로를 재현했다. 같은 부하의 새 복구 결과로 개선 효과를 확인해야 한다.
- LIVE1은 새 역할의 실제 수신 준비가 되지 않았다. 정확한 인증 거부 원인을 별도로 확정하지 않았으며 공개 HBA·Patroni 설정을 바꾸지 않았다. 이후 기존에 검증된 수신 인증 경로로 별도 LIVE2를 실행했다. 인증 값은 기록·게시하지 않았다.
- 실제 LIVE2는 공개 함수 `wait_for_archived_wal`과 실제 Docker Barman 명령을 연결했다. 명령 대역으로 결과를 꾸미지 않았다. 그러나 전체 `gsutil sync` CLI 경로의 실제 실행 증거는 아니다. 해당 원격 메타데이터 계약은 단위 시험으로 검증했다.
- 두 실제 run의 정리 결과 모두 공개 설정 보존·원래 클러스터 복귀·소유 자원 제거가 참이다. 시험용 빈 버킷은 다음 직렬 복구 회차를 위해 유지한다. 활성 객체 삭제와 soft-delete 보존 가능성은 구분한다.

```text
그림 3 — 이어지는 통합 복구 시험의 판정 범위 [계획]

같은 부하: 완료 4 + 중단 Job 1 + 추가 업로드 60
  → 300초 구간마다 필요한 WAL 보관 완료·외부 바이트 확인
  → 마지막 확인 시점의 ACK 개수 기록
  → 원본 경로 취득 중단 → 새 PGDATA 복원
  → Worker·Flyway·수선 전 최초 감사
      ├─ 확인 구간 ACK 누락 > 0: 불합격, Worker 활성화 거부
      └─ 누락 0: Worker 활성화 → 기능별 시간 계측
  → 마지막 확인 뒤 요청은 별도 손실 코호트로 보고
  → 기존 3노드·설정 복구·시험 자원 정리
```

최종 전송을 임의로 추가해 전체 65/65를 만드는 시험이 아니다. 운영 RPO 0·공개 서비스 전환·Ollama 생성 답변까지 검증했다고 주장하지 않는다.
