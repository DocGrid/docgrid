# 업로드 성공 응답과 격리 복원 기능 계측 계획

관련 이슈: #560. 이 문서는 실행 전 기준이며 결과는 회차별 기록으로 구분한다.

## 목적·합격 기준

업로드 성공 응답을 DB 밖에 즉시 기록하고, 장애 이전에 고정한 외부 기준 백업·완성 WAL·GCS 원본 보존본으로 복원한다. 최초 상태 감사가 통과한 뒤에만 버킷 재지정·Flyway·Worker를 허용한다. 후속 인덱싱 결과로 최초 손실을 덮어쓰지 않는다.

| 대상 | 계획한 확인 |
|---|---|
| 기능 코호트 | 실제 BGE 인덱싱 완료 문서 4건, 실제 모델 응답 대기 중 시험 JVM을 강제 종료한 Job 1건 |
| 손실 코호트 | 고유 요청 키의 합성 업로드 60건, 목표 전송 간격 11초. 실제 전송·응답 시각을 원장에 기록 |
| 외부 보존 | 기준 백업·identity와 완성 WAL, 원본 객체의 고정 generation·SHA-256·크기 |
| 주기 비교 | 손실 코호트를 300초 주기의 두 전송 구간 이상에 배치. 전송 지연·누락은 실제 시각으로 보고 |
| 최초 감사 | 요청 키, Document·Version·FileObject·Job ID와 연결, 원본 generation·바이트 대조 |
| 기능 계측 | 기존 다운로드·검색, 중단 Job 재개, 새 업로드·인덱싱·다운로드 |
| 최종 정합성 | 관측된 복원 문서의 미완료 Job·중복 Chunk·중복/누락 Embedding 0건 |
| 정리 | 원래 리더 1대·Standby 2대 복귀, 시험 소유 프로세스·터널·자격 증명 정리, 개인·공개 설정 보존 |

## 환경과 통제 변수

- 코드 기준: `3bff887a5f6abdf4155957a658599f8f0366a141`. Java 제품 코드를 변경하지 않는다. 복원 판정기의 상태 허용 목록은 실제 Java enum에 맞춰 검증한다.
- 로컬 전용 JVM·Valkey·Barman 도구 컨테이너, 실제 실행 중인 BGE-M3, 클라우드의 전용 논리 DB와 시험 버킷을 사용한다. Ollama 생성 답변은 범위 밖이다.
- 새 클라우드 프로젝트에는 이전 백업 VM·카탈로그가 없으므로 시험용 수집기와 기준 백업을 새로 준비한다. 이전 프로젝트의 결과를 이번 준비 상태로 간주하지 않는다.
- 임시 수집기는 영구 replication slot과 Patroni DCS 설정 변경 없이 사용한다. Barman의 두 archiver를 켜되 이 수집기로의 원본 `archive_command` 전송을 추가하지 않고, 실제 스트리밍 경로만 시험한다. 장기 WAL 보존·수신 재연결을 보장하는 운영 구성으로 주장하지 않는다.
- 검색은 장애 전에 완료 문서의 합성 Chunk 본문과 해시를 고정하고, 복원 뒤 기대 문서가 Top 20에 포함되는지 확인한다. 정확한 순위·유사도 점수·검색 품질 개선을 합격 기준으로 삼지 않는다.
- 전송 경계의 요청이 완료된 뒤 WAL을 전환한다. 이 시험의 명시적 제어이며, 작은 쓰기 부하에서 완성되지 않은 WAL을 300초 전송 주기만으로 복구할 수 있다고 가정하지 않는다.
- 설치된 OpenSQL의 기존 비동기 Standby 호스트를 직렬 재사용한다. 복원 중 원래 클러스터는 리더 1대와 동기 Standby 1대로 운영된다. 동기 Standby·리더는 중지하지 않는다. 따라서 완전히 별도인 물리 클러스터 시험은 아니다.
- 실제 DB 중지 전 시험용 프로세스로 자동 복귀 타이머를 검증한다. 대상 역할·프로세스 시작 정보·소유 경로를 재확인하고, 1,800초 자동 원복 장치를 건 뒤 원래 PostgreSQL을 멈춘다. 같은 호스트에서 원래 DB와 복원 DB를 동시에 실행하지 않는다.

## 실행 순서

```text
그림 1 — 변경 전 최초 감사 관문 [계획]

클라이언트 → 요청 키·파일 SHA 기록 → 업로드 HTTP 응답의 ID 4종 기록
     │
외부 보존 → 기준 백업·identity·완성 WAL·원본 generation 고정
     │
원본 접근 상실 T0 → 시험 API 종료·전용 DB 터널 종료
     │                복원 드라이버에서 원본 버킷 I/O 거부 확인
     │                원본에서 복원 자료를 추가 취득하지 않음
     │                원본 버킷의 클라우드 IAM 차단·전체 사이트 소실은 시험하지 않음
     ▼
빈 카탈로그 → 고정 identity 준비 → import·verify → 새 PGDATA 복원
     │
실제 OpenSQL 기동 → SQL·보존 객체 읽기만으로 최초 상태 감사
     ├─ 부분 DB·원본 누락·해시 불일치·기능 코호트 누락 → 활성화 금지·정리
     └─ 관문 통과 → 최초 감사 fsync → 버킷 재지정·Flyway·Worker 기동
```

원본 데이터 접근은 T0 이후 금지한다. 기존 호스트의 역할 확인·자동 원복 제어는 필요하므로, 원래 인프라 전체가 사라진 시험으로 표현하지 않는다.

리허설은 합성 손실 요청 8건·30초 전송 간격의 작은 부하로 먼저 확인한다. 준비 중단·재개로 간격이 달라지면 실제 시각을 기록하고 본시험의 300초 정책 검증에 합치지 않는다.

## 기록과 해석

- 리허설·본시험·재시험의 원장, 카탈로그·PGDATA, 입력 목록과 결과는 분리한다. 준비 실패와 재시도도 숨기지 않는다.
- stdout·stderr는 허용한 이벤트 유형·상태·건수만 기록한다. 원시 앱 로그·연결 문자열·인증정보·내부 자원 식별자는 남기지 않는다. 이 때문에 세부 오류 진단이 제한된 경우를 명시한다.
- T0와 판정기 `cutoff`는 별도 시각이다. 기능별로 두 기준의 경과 시간을 구분한다.
- 유실은 성공 응답별로 대조하고 중간 누락도 확인한다. 결과 불명 요청과 후속 재전송 성공을 원래 성공 응답에 합치지 않는다.
- 보고 범위는 격리 문서 다운로드·검색·인덱싱의 경과 시간이다. 공개 서비스 전환, 전체 사이트 소실, RPO 0 보장, 실제 Ollama 답변 복구를 주장하지 않는다.
