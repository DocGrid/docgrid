# 격리 복원 실행·감사 방법

관련 판정기: [`dr_recovery.py`](../../../scripts/opensql/dr_recovery.py). 이 문서는 이번 실험의 절차이며, 공개 서비스에 그대로 적용하는 자동 복구 매뉴얼은 아니다. 비공개 연산자에는 접속 대상·인증정보가 있으므로 저장소에 포함하지 않는다.

## 실행 전 고정한 조건

1. 전용 논리 DB·계정·시험 버킷을 만들고, 기존 공개 앱의 DB·버킷·Patroni 설정은 유지한다. Java 제품 코드는 `3bff887a5f6abdf4155957a658599f8f0366a141`의 JAR을 사용한다.
2. 로컬 전용 JVM과 Valkey, 실제 BGE-M3, Barman 수집기를 연결한다. 원본·보존본·DB 백업은 서로 다른 시험 버킷을 사용한다.
3. 완료 문서 4건을 인덱싱한다. 다섯 번째 Job에서는 실제 BGE 응답을 제어 프록시에서 보류한 뒤 **시험 JVM만 종료**한다. 합성 벡터나 가짜 검색 결과를 넣지 않는다.
4. Job이 `PROCESSING`, Attempt 1건, Chunk 3건, Embedding 0건인지 SQL로 확인하고 Worker를 끈 시험 API를 다시 시작한다.
5. Barman `check`의 24개 항목과 실제 streaming receiver를 확인한다. 기준 백업 `DONE`, `pg_verifybackup` 종료 코드 0을 확인한다. 사전 보존한 identity와 완성 WAL만 외부에 전송한다.
6. 완료 문서의 실제 합성 Chunk를 검색 입력으로 고정한다. 본문 해시·기대 문서 ID·Top 20 포함 조건을 장애 전에 기록한다. 이는 검색 기능 복구 확인이며 품질 평가가 아니다.
7. 요청 키·파일 해시·크기를 전송 전에, HTTP 응답과 ID 4종을 응답 수신 직후 외부 원장에 기록한다. 60건의 목표 전송 간격은 11초이고 외부 전송 주기는 300초다. 실제 지연은 원장의 시각으로 판정한다.

## T0·입력 동결

- 시험 API 중지 시작 시각을 T0로 기록한다. 수집기와 전용 원본 DB 터널을 종료하고 두 리스너 포트가 닫혔는지 확인한다.
- 복원 드라이버에서 원본 GCS 접근을 거부하는지 확인한다. **버킷 IAM 차단은 시험하지 않았다.** 원본 클러스터는 남아 있으며, 역할 확인·원복·시험 DB 삭제에 필요한 제어 접근은 유지한다.
- 외부 백업·identity·WAL·원본 객체의 generation·SHA-256·크기를 동결한다. 완성되지 않은 `.partial` WAL은 복원 입력에서 제외한다. 이 시점을 판정기의 `cutoff`로 따로 기록한다.
- 입력을 고정한 뒤 source DB·source GCS에서 복원 자료를 추가 취득하지 않는다. 보존본 검증이나 복원 실패를 이유로 이 경계를 이동하지 않는다.

## 최초 감사 전 금지 사항

| 단계 | 실제 연산자가 수행하는 일 | 금지한 일 |
|---|---|---|
| restore | 동결 generation을 새 디렉터리로 다운로드, SHA·크기 대조, 빈 카탈로그에 identity/import, `verify-backup`, 새 PGDATA 생성 | 원본 카탈로그 마운트·원본 DB 연결·ADC를 복원 컨테이너에 전달 |
| target start | 현재 비동기 Standby 역할과 프로세스 시작 정보를 확인, 1,800초 자동 원복 장치 설치, 원래 프로세스 일시 정지, 기존 DB 종료, 같은 라이선스 호스트에서 복원 OpenSQL 기동 | 리더·동기 Standby 정지, 원래 PGDATA 덮어쓰기, 원래 DB와 복원 DB 동시 기동 |
| snapshot | 복원 전용 소켓·포트와 `data_directory`를 확인한 뒤 읽기 전용 SQL, 보존 객체 generation·실제 바이트 대조 | Flyway·Worker·버킷 재지정·수선·재업로드 |
| initial audit | 최초 스냅샷과 감사 결과를 단독 생성·fsync | 후속 정상화 결과로 최초 손실을 덮어쓰기 |

복원 도구 컨테이너는 네트워크를 차단하고, 동결 입력을 새로 받은 디렉터리만 마운트한다. 실제 OpenSQL 서버는 설치된 원래 라이선스 경로를 환경으로 전달받는다. 라이선스 파일을 수정·재발급·다른 호스트에 복사하지 않는다.

## 요청별 대조와 활성화

읽기 전용 SQL은 `initial_upload_requests`를 **사용자 ID + 요청 키**로 찾고, 응답에 기록한 Document·Version·FileObject·EmbeddingJob ID와 관계를 대조한다. 숫자 ID가 우연히 존재하는지만 검사하지 않는다.

- DB 기록 없음: `DB_MISSING`.
- 응답 ID나 연결 관계 불일치: `DB_PARTIAL`.
- DB가 참조하는 보존 원본 없음: `OBJECT_MISSING`.
- 동결 generation·SHA-256·크기 불일치: `HASH_MISMATCH`.
- DB 관계와 원본 바이트 일치: `RESTORED`. 아직 인덱싱 완료라는 뜻은 아니다.

기능 코호트 5건이 모두 `RESTORED`이고 다른 구조·객체·무결성 오류가 없을 때만 활성화한다. 손실 코호트의 `DB_MISSING`은 실제 손실로 남긴다. 그 뒤 **복원 DB만** 보존 버킷으로 재지정하고, Flyway·Worker를 켠다. 복원된 사용자 레코드로 새 로그인해 인증된 HTTP를 사용한다.

## 기능·정합성·정리 판정

| 기능 | 실제 판정 |
|---|---|
| 기존 다운로드 | 완료 문서 4건의 HTTP 200·크기·SHA-256 일치 |
| 기존 검색 | 사전 고정 Chunk 질의, HTTP 200, 기대 문서가 Top 20 안에 포함 |
| 중단 Job 재개 | 같은 Job `INDEXED`, 해당 버전 Job 1개, Attempt 2개 |
| 새 작업 | HTTP 업로드 → `INDEXED` → 다운로드 SHA-256 일치 |
| 최종 감사 | 관측 복원 문서의 미완료 Job·중복 Chunk·중복 Embedding·누락 Embedding 각각 0건 |
| 정리 | 복원 프로세스 종료·기존 Patroni 재개, 리더 1대·동기 Standby 1대·비동기 Standby 1대 확인, 소유 시험 자원 삭제, 원래 설정 해시 대조 |

각 기능의 **실제로 확인한 시각**을 T0와 cutoff 양쪽 기준으로 계산한다. 기능 검사는 순차 실행되므로 그보다 앞서 준비됐을 가능성까지 측정한 것은 아니다. DB를 켠 시각을 전체 기능 복구 시간으로 대체하지 않는다.

GCS의 활성 시험 객체 삭제와 soft delete 보존은 구분한다. 정리 뒤에도 제공자 보존 정책에 따른 삭제 세대가 남을 수 있으며, 물리 소거라고 보고하지 않는다. 기존 개인 환경 파일·기존 모델 컨테이너·공개 원본 버킷은 삭제 대상이 아니다.
