# #456 하이브리드 검색 테스트 결과

- 관련 이슈: #456
- 설계 문서: [kangcheolung-#456-hybrid-search.md](../design/kangcheolung-%23456-hybrid-search.md)
- 측정 증빙: [evidence/issue-456/](evidence/issue-456/)
- 코드 기준: `develop`(`61515ea`)을 병합한 `feature/456`. 자동 테스트는 병합 후 다시 실행했고, 실서버 품질 측정은 병합 전 코드로 했다(병합으로 검색 코드는 바뀌지 않음)

**결론:** 새로 만든 테스트와 기존 검색 테스트 105개는 전부 통과했다. 전체 테스트(1,421개)에서는 2개가 실패했는데, 이번 변경과 무관한 비동기 워커 정리 경쟁 때문에 간헐적으로 실패하는 테스트이고 그 클래스만 따로 돌리면 통과한다. 실제 서버 측정에서는 벡터 단독보다 1위 정답이 82개에서 92개(111개 질문)로 늘었고, 사전에 기준을 고정한 처음 보는 질문 39개에서도 28개에서 32개로 늘었다.

## 1. 테스트 환경

| 항목 | 값 |
|---|---|
| DB | 로컬 Docker PostgreSQL 17 + pgvector (포트 5432, DB `docgrid`). 공유 DB는 사용하지 않음 |
| 통합 테스트 환경변수 | `DB_HOST/DB_PORT/DB_NAME/DB_USER/DB_PASSWORD`를 로컬 컨테이너로 지정, `SPRING_DATA_REDIS_DATABASE=9`, `SPRING_DATASOURCE_HIKARI_MAXIMUM_POOL_SIZE=3` |
| 풀 크기를 3으로 둔 이유 | 전체 스위트가 동시에 연 연결이 PostgreSQL `max_connections`(100)에 닿아 `too many clients`가 난다. 수정 전 `develop`에서도 같다 |
| 마이그레이션 | `develop`의 V44·V45와 이 PR의 V46(`pg_trgm` 확장 + `chunk_text` GIN 인덱스)이 새로 만든 테스트 스키마(`docgrid_test`)에 모두 성공으로 적용된 것을 확인 (`develop`에 V45가 먼저 들어와 있어 이 PR의 마이그레이션을 V45에서 V46으로 바꿨다) |
| 실서버 측정 | 로컬 백엔드(18080) + 임베딩 서버(BGE-M3, 8000). 순위 측정 시 RAG 생성은 일부러 실패시켜 CPU 점유를 제거 |

## 3. 시나리오 검증

### 3.1 정상 케이스

| # | 시나리오 | 기대 | 결과 |
|---|---|---|---|
| N1 | 벡터가 의미로 못 잡는 짧은 용어 질문(`OM은 뭐야?`) | 그 단어가 든 청크가 상위로 올라온다 | 통과. 벡터 단독 7위 → 1위. AI 답변이 "찾지 못했습니다"에서 정답으로 바뀜 |
| N2 | 의미형 질문 | 벡터 단독 순위가 유지된다 | 통과. 사전 고정 기준 ④(의미형 1위·3위 안 모두 이상) 충족 |
| N3 | 흔한 단어만 있는 질문(`STOMP`) | 벡터 단독과 같은 결과 | 통과. 폐기한 첫 설계에서 나빠졌던 `STOMP /app 방향`이 벡터 단독과 같은 순위로 복귀 |
| N4 | 한 문서에 관련 청크가 많은 질문 | 문서당 최대 2개, topK 유지 | 통과 (`HybridSearchQueryServiceTest`) |
| N5 | 실제 서버 검색 API 호출 (`POST /search`, topK 10) | 응답 필드·형식이 기존과 같다 | 통과. 응답 DTO·스키마 변경 없음, 세 세트 131개 질문 호출이 같은 측정 스크립트로 처리됨 |

### 3.2 에러·경계 케이스

| # | 시나리오 | 기대 | 결과 |
|---|---|---|---|
| E1 | 읽기 권한이 없는 문서에 질문 단어가 있음 | 결과에도 문서 빈도(가중치)에도 반영되지 않는다 | 통과 (`권한 누수 방지` 테스트) |
| E2 | 삭제된 문서 / 색인이 끝나지 않은 문서 / 이전 버전 청크 / 비활성 임베딩 / 다른 임베딩 모델 | 결과에 나오지 않는다 | 5종 모두 통과 |
| E3 | 읽을 수 있는 문서가 없음 | DB를 조회하지 않고 빈 목록 | 통과 |
| E4 | 질문에서 뽑을 단어가 없음(한 글자, 불용어뿐) | 단어 쿼리 없이 벡터 유사도 기준만 적용 | 통과 |
| E5 | 검색 범위에 아예 없는 단어만 있음 | 단어 갈래를 건너뛴다 | 통과 |

| E7 | `om`이 `Computer` 안에 들어 있음 | 일치로 보지 않는다 (영문 단어 경계) | 통과 (DB 통합 테스트) |
| E8 | 순차 스캔을 끄고 GIN 인덱스를 강제로 사용 | 같은 결과 | 통과 |

| E11 | 질문 임베딩이 제한 시간을 넘김 | 기존과 같은 `504 SEARCH-004` | 측정 중 RAG 생성이 CPU를 점유했을 때 실제로 발생해 확인(기존 동작). 이를 피하려고 순위 측정 때 생성을 막았다 |

## 4. 검색 품질 측정 (실제 서버, 벡터 단독 → 하이브리드)

질문 세트 3개는 서로 겹치지 않는다. 세트 3은 설계와 판정 기준을 결과를 보기 전에 파일로 고정한 뒤 처음 사용했다(`evidence/issue-456/design-frozen-before-set3.txt`).

| 세트 | 정답이 1위 | 정답이 3위 안 | MRR@10 | 좋아진 / 나빠진 질문 |
|---|---:|---:|---:|---|
| 1 (34개, 설계에 사용) | 26 → 28 | 32 → 33 | 0.847 → 0.887 | 2 / 0 |
| 2 (38개) | 28 → 32 | 33 → 34 | 0.806 → 0.864 | 4 / 1 |
| **3 (39개, 사전 고정 기준)** | **28 → 32** | **32 → 36** | **0.784 → 0.868** | **8 / 0** |
| 합계 (111개) | 82 → 92 | 97 → 103 | 0.811 → 0.872 | 14 / 1 |

사전 고정 판정 기준 4개는 세트 3에서 모두 충족했다.

| 기준 | 세트 3 값 | 판정 |
|---|---|---|
| ① 1위 정답 수 ≥ 벡터 단독 | 32 ≥ 28 | 충족 |
| ② 3위 안 정답 수 ≥ 벡터 단독 | 36 ≥ 32 | 충족 |
| ③ 좋아진 − 나빠진 ≥ 2 | 8 − 0 = 8 | 충족 |
| ④ 의미형(바꿔 쓴 질문) 1위·3위 안 하락 없음 | 1위 8 ≥ 7, 3위 안 9 ≥ 8 | 충족 |

나빠진 질문은 111개 중 1개(`ISP는 뭐의 약자야?`, 6위 → 결과 밖)다.

### 응답 시간

5개 문서(청크 83개) 환경에서 클라이언트 기준 중앙값이 두 방식 모두 약 280~305ms 범위로 큰 차이가 없었다(질문 임베딩 포함). 요청마다 DB 조회가 2번 늘어나므로 청크가 수만 개 이상인 환경은 측정하지 않았다.

## 5. 한계

- 5개 문서, 청크 83개의 작은 환경이다. 질문은 직접 작성했고, 질문 하나가 1위 정답률을 약 3%p 움직인다.
- 세트 1은 설계에, 세트 2는 설계 방향 선택에 영향을 줬다. 최종 설계 고정 후 검증은 세트 3 한 번이다.
- 개선은 짧은 용어·약어 질문에 몰려 있고 흔한 단어만 있는 질문은 달라지지 않는다.
- AI 답변 비교는 12개, 질문당 1회라 사례 확인용이다.
- 실서버에서 플래그를 끈 상태로 다시 측정하지는 않았다(단위 테스트로만 확인).

## 6. 재현 방법

```bash
# 검색 도메인 테스트 (로컬 Docker DB 환경변수 지정 필요)
DB_HOST=localhost DB_PORT=5432 DB_NAME=docgrid DB_USER=docgrid DB_PASSWORD=<로컬 컨테이너 비밀번호> \
SPRING_DATA_REDIS_DATABASE=9 SPRING_DATASOURCE_HIKARI_MAXIMUM_POOL_SIZE=3 \
./backend/gradlew -p backend test --tests '*domain.search*'

# 검색 품질 측정 (로컬 서버를 띄운 뒤)
BENCH_BASE_URL=... BENCH_EMAIL=... BENCH_PASSWORD=... BENCH_COLLECTION=... BENCH_QUESTIONS=questions-set3.json \
python3 docs/test-results/evidence/issue-456/run_search_benchmark.py
```

통합 테스트는 반드시 로컬 DB로 지정해서 실행한다. 지정하지 않으면 기본 접속 정보로 다른 DB에 테스트 스키마를 만들 수 있다.
