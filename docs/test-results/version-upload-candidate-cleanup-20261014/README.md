### 격리 중단 시험의 실제 순서

```text
합성 v1 원본 O1 → 격리 DB에서 v1 INDEXED fixture 구성
합성 v2 요청 → 후보 위치 DB 선기록 → 실제 GCS에 O2 저장
             → DocumentVersionUploadFacade.uploadClaimed(): 저장 반환 직후 중단
             → JVM SIGKILL, HTTP 연결 종료, 사용자는 재시도하지 않음
격리 DB의 후보 등록 시각만 25시간 전으로 변경
  ├─ 삭제 비활성 scheduler: 발견 1, 예약 0, 삭제 0 → O1+O2 유지
  └─ 삭제 활성 scheduler: 발견 1, 예약 1, 삭제 1 → O1만 유지
참조 보호 fixture: O1을 후보로 기록 → 발견 1, 참조 1, 삭제 0
```

중단점은 `DocumentVersionUploadFacade`의 `recoverOrStoreCandidate()` 반환 후 `persist()` 진입 전이다. 후보 정리는 `VersionUploadCandidateCleanupService`가 DB 예약 토큰을 얻고 참조 여부·GCS generation을 확인한 뒤 조건부로 삭제한다. 참조 중인 파일은 삭제하지 않고 후보 기록만 해제한다. 시험에서는 실제 25시간을 기다리지 않고 **격리 DB의 해당 후보 등록 시각만 합성으로 조정**했다. Worker의 인덱싱 완료는 이 실행의 검증 대상이 아니다.

격리 시험의 원본 객체는 SHA-256과 generation **별칭**만 안전한 스냅샷에 남겼다. 종료 시 남은 객체 1개를 generation 조건부로 삭제했고 버킷·컨테이너·임시 자격증명을 제거했다. 삭제 후 객체 수는 **0개**다.

### 공개 서비스 검증의 범위

공개 앱 A/B의 기존 JAR을 각각 백업하고 순차 배포했다. 두 앱의 교체 후 JAR SHA-256은 `c1c5f41dbed359817cb95ac368abf50da5f2a2797c4a7fe57240e7d8c894c4bb`로 같다. 양쪽 `actuator/health`가 HTTP 200을 반환했다. V50이 실행 JAR에 들어 있는 것은 확인했으나 `flyway_schema_history`의 V50 행은 별도 조회하지 않았다. 공개 환경에서 후보 **자동 삭제는 기본값 `false`**이며 이 시험에서 활성화하지 않았다.

브라우저에서 합성 PDF 새 버전 접수 뒤 화면은 버전 2건과 v2 Job `PENDING`을 표시했다. OpenSQL Primary에서 해당 합성 문서의 **v2 버전 1건, 연관 Job 1건, `COMPLETED` 업로드 요청 1건**을 확인했다. GCS 원본은 **637바이트**, SHA-256 `0dd435997995d9b0f8a0318e476d16299ecbee94fed5dbcc9b9773e9354e5500`으로 로컬 업로드 파일과 일치했다. 비공개 버킷·객체 경로·VM 식별자·인증 값은 기록하지 않았다.

**응답 유실 후 브라우저에서 같은 키로 재시도하는 상황은 이번 공개 실행에서 주입하지 않았다.** 기존 로컬 모의 API 브라우저 시험과 GCP API 직접 경로 시험은 별도 기록이며, 이번 공개 정상 업로드를 그 장애 시험의 증거로 해석하지 않는다. v2 Job이 `PENDING`이어서 새 버전의 인덱싱 완료·검색 전환도 확인하지 않았다.

## 실패·재실행과 원시 근거

| 실행 | 관측 | 처리 |
|---|---|---|
| 격리 JAR 준비 R1 | 샌드박스의 Gradle wrapper 잠금 권한 오류 | 권한을 올려 R2 재실행, `bootJar UP-TO-DATE` 성공. 최초 실행 시각은 보존되지 않아 사후 기록에 명시 |
| 공개 배포 확인 사전 탐색 | 앱 VM 이름 패턴 두 차례 불일치. 키 등록 전 실패 | 대상 패턴을 수정해 A/B 각각 한 개를 특정한 뒤 R2에서 수정 전 JAR 확인 |
| 공개 DB/GCS R1 | DB 컨테이너에서 일반 `psql` 명령을 찾지 못해 종료 코드 127 | 기존 OpenSQL 전용 `psql` 경로와 자격 환경을 사용해 R2 재실행. R1·R2 모두 키 삭제 |

각 목적과 재실행은 [`runs/`](runs/)의 별도 안전 로그에 남겼다. `paused_before_db`, `after_crash`, `stale_dry_run`, `after_delete`, `referenced_guard` JSON은 수치와 객체/generation 별칭만 포함한다. scheduler 로그에는 발견·예약·삭제·참조·실패 건수만 보존했다. 콘솔 원본의 비밀값이나 비공개 인프라 식별자는 수집·게시하지 않았다.

## 결론

새 버전 업로드가 GCS 저장 직후 중단되고 사용자가 재시도하지 않아도, **24시간 초과 후보를 정리할 때 미참조 객체만 제거하고 DB 참조 원본을 보존**하는 동작을 격리 실제 GCS에서 확인했다. 공개 환경에서는 수정 JAR 배포 후 **정상 업로드의 화면·OpenSQL·GCS 일치**를 확인했다. 공개 브라우저의 응답 유실 재시도와 Worker 완료 경로는 추가 검증이 필요하다.
