# 응답 유실 뒤 DB 선확인·동일 키 재전송 — `uploadlost01`

- 목적: 서버가 커밋했지만 클라이언트가 최초 HTTP 응답을 읽지 못한 결과 불명 업로드를 실제로 만들고, **재전송 전후** DB·GCS를 대조한다.
- 실행 위치·방법: 운영자 컴퓨터 → IAP 터널 → GCP 앱 A. `verify_initial_upload_retry.py --mode response-drop --run-id uploadlost01`이 HTTP 요청 본문 전체를 전송한 직후 소켓 양방향을 닫고 `getresponse()`를 호출하지 않는다. Primary DB를 읽기 전용으로 확인한 후 앱 B에 같은 키·파일을 재전송.
- 성공 기준: 최초 응답 상태 미관측, 재전송 전 완료 요청·파일·Job 각 1, 재전송 201과 다른 파일 409, 재전송 후에도 각 1, A/B·GCS 원본 SHA 일치.
- 기간: 2026-10-14 00:36:28.575~00:37:26.428 KST. 합성 PDF 623바이트, SHA-256 `ac7cf454bafefe3b23f0a6ef97b09a7afd0ab9b5e291a9676b660b16782f37d7`.

판정: 최초 응답을 읽지 못했지만 DB에는 이미 커밋된 업로드를 동일 키로 재전송해 중복 없이 조회했다. 후속 DB 집계에서 문서·버전·Outbox도 각각 1건이었다. 첫 시도의 HTTP 상태를 추정해 201로 기록하지 않는다. 이 회차는 GCS 저장 직후 앱 종료나 DB Primary 장애 중 응답 유실을 동시에 재현한 것은 아니다.
