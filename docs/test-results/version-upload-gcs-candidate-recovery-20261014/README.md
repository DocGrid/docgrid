# 새 버전 업로드 GCS 후보 복구: 로컬 검증

## 목적과 범위

[#495 수정 전 재현](https://github.com/DocGrid/docgrid/pull/495)에서는 새 버전의 GCS 저장 직후 JVM을 종료했다. 동일 키 재시도 후 v2·Job은 각 1건이었지만 GCS 미참조 객체 1개가 남았다. 이번 변경은 외부 저장 전에 후보 위치를 DB 원장에 기록하고 같은 키의 재시도에서 검증·재사용하며, 오래된 미참조 GCS 후보를 조건부로 정리한다.

이 문서의 실행은 **로컬 단위 테스트와 PostgreSQL 통합 테스트**다. 실제 GCS 버킷에서 #495의 중단 지점을 다시 실행한 결과는 아직 포함하지 않는다.

## 검증된 동작과 한계

- 모의 저장소가 원본 저장 후 앱 종료를 발생시킨 경우 후보 위치가 DB에 남았다. 리스 만료 후 같은 키의 요청은 후보 해시를 확인하고 그 위치로 v2·Job을 각각 1건만 확정했으며, 두 번째 저장소 쓰기를 호출하지 않았다.
- 24시간 지난 미참조 GCS 후보는 기본 설정에서 조회만 했다. 삭제를 명시적으로 켠 시험에서는 generation 조건이 맞는 후보 1건을 삭제했고, DB가 참조하는 후보는 삭제 0건이었다.
- 실제 GCS에 대한 저장·앱 강제 종료·재기동·동일 키 재시도는 **미실행**이다. 따라서 이번 로컬 결과만으로 #495의 GCS 미참조 객체 1건이 실제 환경에서도 0건으로 바뀌었다고 주장하지 않는다.
- 시험용 PostgreSQL 스키마 2개는 삭제 후 잔여 0개를 확인했고, 시험 때문에 시작한 로컬 PostgreSQL 컨테이너는 중지했다. 실제 GCS 객체는 만들지 않았다.
