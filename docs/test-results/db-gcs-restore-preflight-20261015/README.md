# OpenSQL·GCS 시점 복원 준비 상태 점검

## 목적과 판정

2026-10-15 KST, `develop`의 `e1f0de0b143e89fcc2ab06bfe8d939b3bc96dd77`을 기준으로 공개 서비스의 **읽기 전용** 복원 준비 상태를 확인했다. 이 점검은 백업이나 복원을 실행한 시험이 아니다.

**판정: NO-GO — 현재 확보된 근거로는 OpenSQL PITR과 DB·GCS 통합 복원 시험을 시작할 수 없다.** 실제 Primary의 `archive_mode`는 `on`이지만 `archive_command`가 실질적으로 비활성이고 `pg_stat_archiver.archived_count=0`이다. 아카이브 명령을 사용하지 않는 스트리밍 WAL 백업 가능성도 추가 점검했다. Primary의 물리 복제 슬롯 2개와 복제 연결 2개는 모두 활성 상태였지만 백업 이름의 슬롯·연결은 0개였다. 이는 **별도 WAL 수신의 부재를 완전히 증명하지는 않으므로** 기준 백업·연속 WAL 보존본을 실제로 확인해야 한다. DB 3노드에 READY 디스크 스냅샷은 있지만 최신본이 2026-10-10 KST이고 디스크에 자동 스냅샷 일정이 연결되지 않았다. GCS 원본 버킷에는 7일 soft delete가 있으나, 별도 보존본은 이번 점검에서 확인하지 못했다.

## 다음 관문

1. OpenSQL 버전·Patroni 설정과 호환되는 **기준 백업 및 연속 WAL 보관 방식**을 선정하고, 백업을 운영 DB와 분리된 위치에 보관한다. 백업 파일 목록만으로 통과 판정하지 않고 격리 DB에서 기준 백업과 WAL을 실제 복원한다.
2. GCS 원본의 **독립 보존본**과 `provider/bucket/objectKey/size/SHA-256` 원장을 준비한다. soft delete 7일은 장기 백업으로 간주하지 않는다. 원본 복원 시 새 generation이 생길 수 있으므로 복원 후 실제 바이트를 재검증한다.
3. 격리 환경에서 DB를 지정 시점으로 복원하고, DB가 참조하는 원본의 누락·해시 불일치가 0건일 때만 백엔드·Worker를 시작한다. 이후 다운로드·검색·새 업로드 및 실제 RPO/RTO를 측정한다.

이번 점검으로 WAL 설정이나 GCS 보존 정책을 변경하지 않았고, 새 백업·복원 자원도 만들지 않았다. 세 회차의 임시 OS Login 공개키와 로컬 개인키는 각 조회 직후 삭제했다.
