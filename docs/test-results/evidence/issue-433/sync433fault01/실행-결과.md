안전 이벤트 원장에는 201·실패·결과 불명을 별도 종류로 기록했다. `ha_evidence.py verify`는 `complete=true`, 5,401건을 반환했다. `events.jsonl.gz`·`requests.csv.gz`의 요청 ID를 `db-counts.csv.gz`와 대조했고, 대조 수치는 `reconciliation.json`에 남겼다. `k6-events.jsonl.gz`는 수집기의 허용 필드 검사를 거친 원래 k6 이벤트다. `계측-1초.csv`·`host-samples.csv`는 부하 발생기 계측이며 DB·앱 CPU는 이 실행에서 직접 계측하지 않았다.

주입: 10:10:21.705 UTC. 첫 HTTP 500: 10:10:21.834, 첫 503: 10:10:39.118. 마지막 500: 10:10:44.694, 마지막 503: 10:11:27.751. 가장 긴 201 공백은 10:10:21.661~10:11:25.553. 마지막 결과 불명은 10:11:42.083. 10:11:57.599에는 다른 standby 1대가 `sync`·`streaming`으로 관측됐다. 독립 타이머가 10:12:05.332에 규칙을 제거했고, 10:12:28.924에는 replica 2대가 다시 streaming이었다. 동기 standby 재선정의 **정확한 내부 시각**은 수집하지 않았으므로 201 재개 시각과 혼동하지 않는다.

시험 범위는 **복제 링크 상실**이다. standby VM 전체 중단, etcd·OpenProxy 장애, 두 standby 동시 상실, 승격 시 RPO를 시험했다고 해석하면 안 된다. 장애 중 201이 0건인 구간이 있었으므로 “대체 standby가 있어 무중단”이라는 주장은 반증됐다. 자동 쓰기 재시도는 켜지지 않았다. 결과 불명 5건의 DB 반영은 멱등 키 없는 재시도의 위험을 보여준다.
