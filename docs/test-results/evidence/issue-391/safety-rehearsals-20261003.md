# OpenProxy 복구 가드 리허설 기록

시각은 UTC(+00:00)다. 두 리허설은 실제 쓰기 부하 없이 proxy-a만 대상으로 수행했고, 정상 부하·장애 시험 횟수에 포함하지 않는다. proxy-b와 DB 프로세스는 중단하지 않았다.

| 실행 ID | 목적·위치 | 명령·방법 | 관측 결과 | 판정 |
| --- | --- | --- | --- | --- |
| `p391reha` | A 복구 명령 최초 점검, 프록시 A 호스트 | `docgrid-openproxy-fault arm → stop → recover` | 최초 복구 명령에서 런타임 상대경로 쓰기 `Permission denied`; 작업 디렉터리를 명시한 뒤 수동 복구해 단일 프로세스·포트 ready 확인 | **실패·수정**. 부하 시험 미실행. 정확한 시작·종료 시각은 보존하지 않아 RTO 자료로 사용 불가 |
| `p391autoa` | 타이머 자동 복구 점검, 프록시 A 호스트 | 35초 가드 → 프로세스 중단 → 44초 대기 → 상태 확인 | 2026-10-02 16:21:58 중단; 16:22:42 상태 조회 시 아직 down. 수동 복구와 타이머 실행이 거의 동시에 일어나 16:22:43 ready. systemd 로그의 타이머 실행 시각은 16:22:42 | **판정 불가**. 자동 복구 단독 성공을 주장하지 않음. 타이머 기본 실행 허용 오차를 1초로 축소 |
| `p391auto2` | 수정한 타이머 단독 검증, 프록시 A 호스트 | `arm ... 35` → `stop` → 45초 동안 수동 개입 없음 → `status` → 안전한 `cancel` | 2026-10-02 16:24:26 중단, 16:25:11 조회 시 live process 1·port ready·guard armed. 이후 timer 취소, guard absent | **통과**. 관측 창 45초 내 자동 복구. 정확한 재기동 순간은 별도 고빈도 계측하지 않아 35초라고 주장하지 않음 |

첫 리허설에서 복구가 실패했을 때 다음 장애 주입을 멈추고 원인을 확인했다. OpenProxy 실행 작업 디렉터리를 설치 디렉터리로 명시하자 `Permission denied`가 없어졌고, 복구 명령이 정상 상태까지 도달했다. 두 번째 리허설 뒤 proxy-a·proxy-b 각각 live process 1·port ready를 확인했다. 가드는 DB 컨테이너나 PostgreSQL 프로세스를 종료하지 않는다.

공개 증거에는 내부 주소·계정·원시 systemd 로그를 넣지 않았다. 위 시각과 상태는 실행 도중 호스트의 UTC 시각·가드 상태 및 systemd unit 결과를 읽어 기록했다.
