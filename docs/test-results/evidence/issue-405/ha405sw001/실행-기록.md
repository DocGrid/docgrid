# 부하 중 계획된 OpenSQL primary 역할 이전

- 실행 ID: `ha405sw001`
- 목적: 100 req/s HTTP 쓰기 도중 primary를 계획 이전할 때 앱의 실패·결과 불명·안정적 회복·201 응답 데이터 보존을 측정한다.
- 위치: GCP 내부 k6 VM → 내부 LB → 백엔드 A/B → OpenProxy A/B → OpenSQL 3노드. Patroni 이전 명령은 기존 primary VM에서 실행한다.
- 계획 부하: `run_ha_probe_k6.sh ha405sw001 100 90s <내부 LB> <0600 단기 JWT> primary-switchover`.
- 안전 관문: 한 primary·두 streaming replica, 후보 lag 0, nofailover=false, etcd 3/3, READY 부팅 디스크 snapshot, 앱 LB 2/2, 계정 정리 타이머 3/3.
- 완료 조건: 이전 후 단일 primary·두 streaming replica 재합류, 합성 계정 0명·타이머 0/3. HTTP별 결과·request_id DB 대조·RTO 관측을 별도 판정한다. 실패 시 나머지 장애 유형을 진행하지 않는다.
- 관측: k6는 2026-10-03 13:39:56~13:41:26 UTC에 100 req/s로 9,001건을 실행했다. HTTP 201 9,001건, 실패·결과 불명·드롭 각 0건, p95 52.64 ms. 새 primary의 request_id 대조에서 9,001개가 각 1행이고 누락·중복 0건이었다. 이후 leader 1·streaming replica 2, timeline 6 및 시험 계정 0명·타이머 0/3을 확인했다.
- **시간 관문 실패:** Patroni `history --format json`의 timeline 5 종료/새 timeline 6 승격 시각은 **13:42:05.587 UTC**다. 이는 k6 종료 **39.6초 후**다. 원장의 `fault start`는 원격 명령 준비 시작 시각(13:40:59.909 UTC)이고 실제 승격 시각이 아니다. 따라서 9,001건의 무오류·보존은 **장애 전 쓰기 결과**이며, 이 실행으로 부하 중 switchover RTO/RPO를 판정하지 않는다.
- 조치: 부하 시간을 늘리고 원격 명령 준비를 먼저 끝낸 별도 실행 ID에서 재시험한다. 이 실행은 실패/불완전 증거로 보존하며 성공 사례에 합산하지 않는다.
