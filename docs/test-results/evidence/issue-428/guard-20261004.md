# 실행 기록: 독립 etcd 자동 재개 가드

- 시각: 2026-10-04 UTC.
- 위치: node2·node3 VM 호스트의 systemd. DB 컨테이너의 etcd PID만 대상.
- 목적: 로컬 SSH 세션이 끊겨도 `SIGSTOP`된 etcd 프로세스가 정해진 시간 안에 `SIGCONT`를 받을 수 있는지 확인.
- 성공 조건: 정상 etcd 상태에서 타이머를 무장하고, 호스트 서비스의 `Result=success`·프로세스 `running`·안전한 타이머 해제를 확인.

| 단계 | 실제 결과 | 해석 |
| --- | --- | --- |
| 가드 SHA-256 비교·설치 | node1·2·3 전송본이 로컬 스크립트와 동일; 각 VM의 단일 etcd PID 식별 | 다른 프로세스를 대상으로 삼지 않음 |
| node2 무해 시험 `arm … 30` | 타이머 armed; 서비스 `Result=success`, `ExecMainStatus=0`; 이후 `etcd_process=running` | 호스트 타이머가 실제 복구 명령을 실행 |
| node3 무해 시험 `arm … 30` | 타이머 armed; `etcd_resumed_utc=05:51:36.686Z`, `etcd_process=running` | 반대쪽 VM에서도 독립 실행 확인 |
| 한 멤버 시험 | node3 자동 타이머를 먼저 무장 → PID 일시정지 → 수동 재개 → 타이머 해제 | 실제 장애 때 독립 원복 수단이 대기 |
| 두 멤버 시험 | node2·3에 각각 120초 타이머 무장 → etcd PID만 중지 → 재개 뒤 타이머 해제 | 양쪽 가드는 서로 다른 VM의 systemd에 존재 |
| 최종 상태 | node2·3 모두 `etcd_process=running recovery_guard=absent` | 멈춘 PID·활성 타이머 잔류 0 |

정확성 한계: 무해 시험에서 표시한 `etcd_resumed_utc`는 주기적 타이머의 **마지막 관측 실행**일 수 있어 최초 발화 지연 시간으로 쓰지 않는다. host systemd가 함께 고장나는 VM 장애는 이 가드의 범위 밖이다. 가드의 실행 로그 원문은 내부 컨테이너 식별자를 포함할 수 있으므로 외부로 복사하지 않고, allowlist 상태·종료 코드만 기록했다.
