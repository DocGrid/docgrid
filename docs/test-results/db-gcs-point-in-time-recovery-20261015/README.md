# OpenSQL·GCS 격리 시점 복원 실행 기록

## 판정과 범위

2026-10-15 KST에 **OpenSQL 기준 백업·연속 WAL에서 지정 시점 T로 실제 복원**하고, 독립 GCS 사본을 별도 복원 버킷에 복사해 바이트와 DB 참조를 대조했다. 시험용 쓰기 A는 T 이전, B는 T 이후에 커밋했다. 복원 DB에는 **A 1건·B 0건**, 원래 클러스터에는 시험 중 **A 1건·B 1건**이 관측됐다. 복원 DB의 GCS `FileObject` 91건과 문서 버전 참조 96건에 필요한 객체는 독립 사본에 모두 있었고, 별도 복원 버킷의 92개 객체는 SHA-256 재계산에서 **92/92건 일치**했다. 격리 DB의 버킷 참조 91건만 복원 버킷으로 바꿨고 원래 DB는 변경하지 않았다.

**서비스 복구 완료나 RPO/RTO 달성으로 판정하지 않는다.** 격리 백엔드·Worker를 기동해 다운로드·검색·새 업로드·Job 재개를 검증하지 않았고, 앱 사용자가 다시 요청할 수 있는 시간도 측정하지 않았다. 백업 카탈로그와 GCS 사본은 보존했지만, GCS 사본은 **한 시점의 복사**이며 지속 동기화가 아니다. WAL 수신은 시험 당시 Primary에 연결되어 있고 Primary 교체 시 자동 재연결은 검증하지 않았다.

아래 `runs/` 문서는 실행 중 도구가 반환한 필터링된 수치와 상태를 토대로 작성한 **사후 요약 기록**이다. 각 명령의 전체 원시 표준 출력은 별도 파일로 보존하지 못했다. 비공개 GCS 원장은 객체별 해시·generation 대조에 사용했으며 공개 저장소에는 원장 원문을 올리지 않았다. 따라서 공개 기록만으로 모든 원시 이벤트를 독립 재계산할 수는 없다.

## 대상과 실행 방법

- DB: 운영 3노드 OpenSQL 클러스터의 Primary에서 기준 백업과 WAL 수집. 격리 실행에는 기존 라이선스가 허가된 Standby 호스트 한 대를 **순차적으로** 사용했다. 원래 Standby의 PostgreSQL과 Patroni만 멈추고, 별도 데이터 경로·localhost 포트에서 복원본을 실행했다. 원래 데이터 경로는 덮어쓰지 않았다.
- GCS: 운영 원본 버킷 → 별도 비공개 백업 버킷 → 별도 비공개 복원 버킷. 객체 키·크기·generation 및 바이트 SHA-256을 비공개 원장으로 대조했다. 운영 버킷에서 객체를 삭제하거나 교체하지 않았다.
- 백업 수신: 외부 IP 없는 전용 VM, IAP 접속, 설치 시에만 임시 NAT. Barman 기준 백업과 연속 WAL을 수집했고, 물리 복제 슬롯의 WAL 보존 상한을 4GB로 설정했다.
- 자격: 실행 때마다 30분 만료 OS Login 키를 등록하고 종료 시 삭제 절차를 실행했다. 사후 프로필에는 기존 키 7개가 보이지만 개별 키의 생성 시점이 없어 시험 키 제거를 독립적으로 귀속해 증명하지 못했다. 공개 기록에는 실제 인프라 식별자·객체 키·개인정보·자격값을 넣지 않았다.

## 핵심 결과와 해석

1. **DB 시점 선택:** T 전후 3초 간격으로 넣은 합성 행은 복원 DB에서 A만 남았다. 이는 OpenSQL 바이너리로 지정 시점 WAL 적용을 실제 실행했다는 근거다. 기존 문서 행은 시험 사이 변동이 없었으므로 91개 파일 참조의 지문 일치는 보조 정합성 근거이며, 실제 문서 쓰기 전후의 RPO 증거는 아니다.
2. **GCS 독립성:** 원본 92개를 별도 백업·복원 버킷으로 복사했고, 복원 버킷의 실제 바이트를 다시 읽어 92개 모두 SHA-256을 맞췄다. 복원 DB가 참조한 파일은 91개이므로 여분 객체 1개는 서비스 참조 대상과 구분했다.
3. **버킷 재바인딩:** 복원 DB의 `file_objects.bucket_name`만 복원 버킷으로 91행 수정했다. 참조 대상의 객체 키·크기·해시 지문은 동일했다. 업로드 후보는 최초·새 버전 모두 0건이어서 이번 실행에서 후보 generation 재매핑은 필요하지 않았다.
4. **운영 복구:** 두 차례 허가된 Standby의 짧은 중단(약 7초·6초) 후 3노드 상태로 돌아왔다. 각 시험 전에 자동 원복 타이머를 설치했고 종료 뒤 제거했다. 사용자 API 가용성이나 쓰기 공백은 계측하지 않았다.

## 남은 경계와 다음 결정

- 격리 백엔드·Worker로 실제 다운로드·현재 버전 검색·신규 업로드·미완료 Job 재개를 시험한 뒤에만 **서비스 복구**를 주장할 수 있다.
- GCS 원본 사본은 일회성이다. 지속 복사·보존 정책과 DB WAL 시점에 필요한 객체의 포괄 범위를 설계해야 한다.
- Barman 수신기는 시험 당시 Primary에 종속된다. Primary 장애·승격 후 백업 대상과 슬롯을 옮기는 절차, 수신 중단 경보, 4GB WAL 보존 상한 도달 시 행동을 별도로 시험해야 한다.
- 의도적으로 T 이후의 합성 행 B가 빠진 것은 예상 결과다. 이를 실제 운영 RPO(손실 시간)나 서비스 RTO(사용자 경로 복구 시간)로 환산하지 않는다.
