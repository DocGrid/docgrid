# 외부 보존본 기반 DB·GCS 격리 복원 시험 계획

## 범위와 성공 기준

- 실행 ID 접두사: `DR-OFFSITE-20261017`. 각 목적과 재시도에 별도 번호를 부여한다.
- 대상: 시험용 OpenSQL 클러스터와 비공개 GCS 보존본. 원본 DB 및 문서 원본 버킷은 복원 대상으로 사용하지 않는다.
- DB 입력은 외부 DB 백업 버킷의 `complete.json`이 가리키는 Barman export와 완성 WAL·timeline history만 사용한다. 백업 VM 로컬 기준 백업·WAL은 복원 입력에서 제외한다.
- GCS 입력은 지속 보존 버킷에서 읽는다. 이전 일회성 복원 버킷의 사본은 제외한다.
- 성공: 선택한 시점까지의 DB 시험 마커와 `file_objects` 참조를 격리 DB에서 확인하고, 그 참조의 보존본 바이트·SHA-256을 대조한다. 격리 백엔드에서 다운로드와 검색을 확인한다. 원래 클러스터가 리더 1대·스트리밍 Standby 2대로 복귀한다.
- 복원 가능 시점이 백업·완성 WAL의 연속성 또는 GCS 사본 시점과 맞지 않으면 실행을 중단하고 수치와 원인을 기록한다. RPO 0 또는 운영 환경 복구를 주장하지 않는다.

## 실행 후 범위 차이

시험 기준 소스는 `develop`의 `5d9042ae3ef7e9c2c0b183f5d9f669480a76a0f7`이다. 단계별 실행 절차와 수치는 개별 로그에 남겼다. 원격 실행에 쓴 일회성 Python 스크립트에는 비공개 환경 경로가 포함돼 저장소에 싣지 않았으므로, 공개 기록만으로 명령 바이트를 재실행할 수는 없다.

계획한 검색·미완료 Job 처리까지의 사용자 기능 검증은 수행하지 못했다. 이번 실행은 실제 보존 GCS를 이용한 **기존 문서 다운로드**까지 확인했다. 검색은 별도 임베딩 모델과 RAG Worker 경로가 필요하고, 새 업로드는 30일 최소 보존 버킷에 시험 객체를 남기므로 이 격리 복원 회차에서 추가하지 않았다. 이 한계를 숨기지 않고 최종 요약의 미검증 범위로 남긴다.
