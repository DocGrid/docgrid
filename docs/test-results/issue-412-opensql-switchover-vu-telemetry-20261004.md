# 부하 중 OpenSQL 계획 역할 이전 재시험: 부하 발생기 미전송과 HTTP 500 분리

- 이슈: [#412](https://github.com/DocGrid/docgrid/issues/412)
- 범위: GCP 시험용 OpenSQL 3노드의 **계획된** primary switchover. VM 상실·PostgreSQL 강제 종료·etcd 장애는 수행하지 않았다.
- 실행: 2026-10-03 16:36–17:17 UTC (2026-10-04 01:36–02:17 KST). 모든 수치는 이 실행의 관측값이다.
- 결론: 초기 VU 40→280→400을 분리한 재시험에서 k6 미전송은 **167→39→0건**으로 줄었다. 마지막 실행의 HTTP 500은 여전히 **85건**이다. 성공 응답(201)의 최종 DB 누락·중복은 네 실행 모두 **0건**이었다. **미전송 해결은 앱 무오류를 뜻하지 않는다.**

## 왜 다시 시험했나

앞선 switchover 부하 시험에서 k6의 `dropped_iterations`가 있었다. 이는 서버가 요청을 실패시킨 것과 달리 **부하 발생기가 요청을 보내지 못한 것**이다. 둘을 HTTP 장애로 합산하면 실제 서비스의 실패율과 회복 시간을 잘못 읽는다. 이번 시험은 같은 70 req/s, 같은 180초 전환 실행에서 1초별 k6 VU·대기·CPU·메모리와 독립 요청 원장을 결합했다.

```text
그림 1 — 두 종류의 실패를 분리한 실제 경로

GCP 내부 k6 (목표 70 iteration/s)
  ├─ VU를 얻지 못함 → dropped_iterations
  │                    HTTP 전송 자체가 없으므로 서버 500이 아님
  └─ VU 확보 → request_id가 있는 HTTP 쓰기
                    │
                    ▼
            내부 LB → 백엔드 A/B → Hikari
                    │
                    ▼
            OpenProxy A/B → OpenSQL primary
                    │
                    ├─ HTTP 201: 외부 원장에 기록 → 새 primary의 DB 행과 대조
                    └─ HTTP 500: 실패 원장에 분리 → DB 반영 여부 별도 대조
```

## 사전 안전 관문과 판정 방법

매 실행 전 DB VM 3/3, leader 1·streaming replica 2·복제 지연 0 MB, etcd 3/3, 앱 LB 2/2, 승격 후보, 세 DB 디스크의 READY snapshot, 합성 계정 정리 가드 3/3을 확인했다. 설치 버전과 Patroni 설정은 [사전 점검](evidence/issue-412/00-preflight.md)에 남겼다. snapshot은 복구 지점의 존재이지 전체 클러스터 복원의 실증은 아니다.

- 정상 기준선: 70 req/s × 60초, 미전송 0·HTTP 오류 0·201 ID마다 DB 1행.
- 장애 실행: 70 req/s × 180초. 첫 실행 초기 VU 40, 둘째 280, 셋째 400; 최대 VU 800, 요청 timeout 10초. 계획 이전은 각 실행에서 단 한 번 수행했다.
- 원장: k6가 보낸 `request_id`·HTTP 결과를 DB 밖에 보존하고 새 primary에서 ID별 행 수와 대조했다. 201 누락, 201 중복, 500의 DB 반영, DB 고아 행을 별도 집계했다.
- 전환 시각: `fault start` 이벤트는 명령 준비이므로 승격으로 간주하지 않고, Patroni history의 새 timeline 승격 시각을 사용했다.
- 시간대: 원본 timestamp를 UTC 초로 정규화해 k6 숫자 Point와 VM의 1초 CPU·메모리 샘플을 연결했다. 원본과 요약은 별도 보존했다.

```text
그림 2 — 요청 ID별 정합성 판정

외부 원장                           복구 후 새 primary
  201 + request_id ───────────────────▶ DB 행 수 확인
       ├─ 1행: 이 실행에서 보존 관측
       ├─ 0행: 성공 응답 데이터 누락
       └─ 2행 이상: 중복 반영

  500 + request_id ───────────────────▶ DB 반영 수 별도 집계
       ├─ 0행: 미반영 관측
       └─ 1행 이상: 실패 응답이어도 커밋 가능성을 조사해야 함

  dropped_iterations: request_id·HTTP 요청이 생성되지 않음
       → DB의 누락 건수에 넣지 않음
```

네 실행 모두 결과 불명 요청·DB 고아 행은 **0건**이었다. 장애 실행의 HTTP 500은 각각 DB 반영 **0건**으로 관측됐다. 이 결과만으로 모든 장애 시점의 쓰기 자동 재시도가 안전하다고 일반화하지 않는다. 마지막 실행은 실패율 약 0.67%로 k6의 `http_req_failed < 1%` 임계값을 통과해 종료 코드 0이었으나, **서비스 무오류 판정은 실패**다. 장애 실행의 외부 원장 `normal_baseline_pass=false`도 정상 기준선 규칙 때문에 예상된 값이며 201 보존 실패와 다르다.

```text
그림 3 — 부하 발생기 VU를 늘렸을 때의 관측

각 실행: 70 req/s, 180초, 최대 VU 800, timeout 10초
                 초기 VU     미전송       HTTP 500
  계획 이전 A       40         167건         68건
        ↓
  계획 이전 B      280          39건         88건
        ↓
  계획 이전 C      400           0건         85건

마지막 실행: 활성 VU 최대 354 < 초기 확보 400
  → 이 실행에서는 신규 VU 확보 지연 없이 전송 슬롯을 채움.
  → 세 실행은 방향·시각이 달라 VU만의 엄격한 인과 비교는 아님.
  → 500은 별개의 서버·연결 장애로 남음.
```

첫 계획 이전의 미전송은 승격 인접 6초에 167건 집중됐고, VU 280 실행은 3초에 39건 집중됐다. 해당 초의 VU 대기 p95는 최대 약 **5.0초**, k6 VM CPU는 각각 최대 약 **9.09%**, **10.05%**였다. 전체 실행의 k6 CPU 최대는 첫 이전 **28.92%**, VU 280 **61.84%**, VU 400 **55.86%**였다. 따라서 CPU 포화만으로 미전송을 설명하기보다, 전환 중 긴 요청으로 VU 점유가 늘어난 영향이 유력하다. 이는 **관측에 근거한 해석**이지 단독 원인 증명은 아니다.

동시 요청 중에는 일부 201이 계속 나왔으므로 “그 시간 내내 모든 쓰기가 중단됐다”는 뜻은 아니다. 이 값은 **관측된 요청의 회복 경계**이며 보편적인 RTO 상한이나 무손실 RPO 보증이 아니다. 계획된 역할 이전 세 건에서 timeline 8→9→10→11, 이전 리더의 streaming 복귀, 최종 단일 leader를 확인했다.

```text
그림 4 — 승격과 HTTP 결과의 시간 경계

fault start 이벤트
  │  운영 명령 준비를 원장에 남김
  │  실제 DB 승격이 완료된 시점은 아님
  ▼
Patroni planned switchover → history에 새 timeline·새 leader 기록
  │
  ├─ 기존 연결·진행 중 트랜잭션 일부 → HTTP 500
  ├─ 생존 경로의 동시 요청 일부      → HTTP 201
  └─ 연결 재설정·새 primary 라우팅 → 안정적인 201 재개

별도 확인:
  201 원장 ↔ 새 primary request_id: 누락·중복 0건
  500 원장 ↔ 새 primary request_id: 이번 실행들에서 반영 0건
```

## 계측기 자체의 실패와 복구

첫 정상 실행의 원본 k6 Point에 소수점 이하 **5자리** timestamp가 있었고, GCP 부하 VM의 Python 3.9 계측기는 6자리 초과만 잘라 처리해 요약이 종료 코드 **1**, runner가 **98**로 끝났다. k6 본체와 4,200건 요청은 성공했다. 원본을 지우지 않고 계측기의 UTC 정규화를 **소수 1–9자리 → 6자리**로 보정했고, 같은 원본으로 재요약해 4,200건·미전송 0·호스트 샘플 61개를 복구했다. [원본 실패 기록](evidence/issue-412/ha412b070a/실행-기록.txt), [재요약 결과](evidence/issue-412/ha412b070a/계측-요약-복구.json), [단위 회귀](evidence/issue-412/local-parser-01.md)를 함께 보존한다.

이후 runner에 **선택적 초기 VU 인수**를 추가했다. 미지정 시 종전 40을 유지한다. 허용 범위 밖 인수는 실행 전에 거부한다. 로컬 Python 계측 시험 **7/7**, OpenSQL Python 시험 **84/84**, Bash 구문 검사와 유효 토큰 파일로 재검증한 잘못된 VU 입력 차단이 통과했다. [로컬 재검증](evidence/issue-412/local-suite-02.md)과 [공개 전 재실행](evidence/issue-412/local-suite-03.md)을 분리해 기록했다.

## 기록, 정리, 남은 문제

각 실행에 한국어 [실행 결과](evidence/issue-412/ha412sw400c/실행-결과.md), 원장 `requests.csv.gz`, DB 대조 `reconciliation.json`, 1초 지표 `계측-1초.csv`, 호스트 샘플, k6 원시 Point를 분리해 남겼다. 공개 근거에서 프로젝트 ID·내부 IP·개인 식별자·JWT·암호를 제외했고 압축은 **원본과 byte 동일함을 확인한 무손실 gzip**이다. 원본 포인트의 비어 있지 않은 tag는 네 실행 모두 **0개**다. [종료·접근 정리](evidence/issue-412/01-cleanup.md)에 임시 SSH 키·JWT·합성 계정·정리 가드 제거와 최종 상태를 기록했다. **DB 3대·앱 2대·공유 캐시 1대·부하 VM 1대는 이후 시험을 위해 계속 실행 중**이며 시험 종료 시 중지하지 않았다.

- 해결: k6 미전송 계측 오류 수정, 초기 VU 사전 확보에 따른 미전송 **0건** 실행 확보.
- 미해결: switchover 도중 앱 HTTP 500 **68/88/85건**. 원인은 이 시험만으로 확정하지 않는다. 기존 [HTTP 500 조사 이슈 #393](https://github.com/DocGrid/docgrid/issues/393)에서 SQLSTATE, 커넥션 폐기·재획득, 요청 단계의 비식별 로그를 추가해 확인해야 한다.
- 범위 밖: 비계획 PostgreSQL 프로세스 종료·리더 VM 상실, etcd 정족수, Worker 멱등 복구, 장기 반복 시험. 이번 201 누락 0건을 그 상황의 RPO 0 보장으로 확대하지 않는다.
