# VERSION-UI-BROWSER-20261014-01 — v2 응답 불명 뒤 동일 키 재시도

- 시각: 2026-10-14 약 03:45~03:48 KST
- 목적: 실제 브라우저 화면이 v2 업로드의 502 응답 뒤 같은 키·파일을 재전송하고, 실제 DB의 버전·Job이 각각 한 번만 늘어나는지 확인
- 위치·개정: 로컬 Vinext 프론트엔드, 시험용 응답 교체 프록시, `test` 프로필 백엔드, 격리 PostgreSQL 17.8과 로컬 파일 저장소. 소스는 `b00b0506f31f9ac26844208cee6fb2319f947502` 기준 작업트리 변경.
- 방법: 합성 TXT 97바이트로 문서 v1을 만들고 시험 준비를 위해 v1·Job을 `INDEXED`로 전환. 브라우저에서 합성 v2 TXT 97바이트를 선택해 업로드했다. 프록시는 백엔드 201을 확인한 뒤 첫 브라우저 응답만 502로 교체하고, 두 번째 요청은 원래 응답을 전달했다. 각 시점의 DB 건수를 SQL로 조회했다.
- 성공 기준: 첫 502 뒤 같은 업로드 재시도 버튼과 잠긴 파일 입력 표시; 두 POST의 키·파일 지문·결과 ID 일치; 최종 문서의 버전·Job 2건, 최대 버전 번호 2, 완료 키 1건, 버전 Outbox 2건.

## 범위와 정리

프록시는 백엔드가 **이미 201을 반환한 뒤** 브라우저에 502를 보냈다. 따라서 이 결과는 응답을 알 수 없는 업로드의 재시도이며, DB 커밋 중단이나 네트워크 연결이 완전히 끊긴 시나리오는 아니다. v1의 `INDEXED` 상태는 시험 준비를 위해 DB에서 직접 설정했으며 Worker가 실제 인덱싱한 결과로 주장하지 않는다. GCP·OpenSQL·GCS 경로를 통과하지 않았다. 원장에는 요청 키 원문, 인증 헤더, 시험 계정 비밀번호, 파일 본문을 보관하지 않았다.

시험 준비 중 첫 프록시 실행은 샌드박스의 루프백 바인딩 제한으로 시작되지 않았다. 권한을 부여한 재실행에서 서버가 준비됐고, 브라우저는 `127.0.0.1` URL 연결을 거부한 뒤 `localhost` URL로 정상 접속했다. 이 두 시도는 업로드 POST를 만들기 전의 환경 준비 실패이며 성공 실행의 표본에 섞지 않았다.

시험 종료 후 브라우저 탭·프론트·프록시·백엔드를 닫고 격리 PostgreSQL 컨테이너를 중지했다. 루프백 서비스 포트 4개가 모두 닫힌 것을 확인했고, 임시 자격증명과 합성 파일 디렉터리를 제거했다. 비식별 원장과 화면 캡처 3개 파일만 결과 디렉터리에 보존했다.
